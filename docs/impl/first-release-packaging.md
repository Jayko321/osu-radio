# Первый релиз: Windows Setup и два Arch-пакета

Статус: объём пересогласован 2026-10-29; T01–T04 реализованы с указанными
в карточках ограничениями. T05 реализована для Arch; runtime проверен,
Qt-проверка частичная. T06 отложена; T07 проверена на candidate-входах.
Нативная Windows-проверка и итоговая приёмка не выполнены.
Дата исходного согласования: 2026-10-27.

Изменение от 2026-10-29: первый релиз — Windows Setup, `osu-radio-bin` и
`osu-radio-git` для Arch. Windows — основная пользовательская платформа.
AppImage, Ubuntu и универсальная Linux-переносимость отложены. Бинарный архив
для `-bin` обязателен; прошлые результаты Ubuntu не подтверждают новый Arch-комплект.

## 1. Источник, цель и существующая основа

Источник требований — [first-release-packaging.md](../specs/first-release-packaging.md), R1–R9.

Результат: пользователь устанавливает или запускает готовый комплект, добавляет
stable/lazer и слушает музыку без подготовки `.env`, сервера, БД или SDK.

Существующая основа:

- [EmbeddedServer](../../crates/osu-radio-client/src/server.rs) уже находит сервер
  рядом с GUI или в PATH, управляет готовностью и завершением. T02 расширила
  отключение `.env` на Windows; нативная проверка открыта.
- [ServerConfig](../../apps/osu-radio-server/src/config.rs) предоставляет SQLite
  fallback на Linux и Windows (T02); тесты конфигурации и запуска изолируют окружение.
- [Lazer reader](../../crates/radio-scanner/src/lazer/scanner.rs) использует runtime
  override, установленный путь относительно executable, затем build-time fallback
  (T03). Существующие проверки покрывают NDJSON, настоящие
  синтетические Realm-файлы, ошибки и очистку процесса.
- [Arch-рецепт](../../packaging/arch/PKGBUILD) содержит подходящую системную
  раскладку, но закреплён на старом релизе и .NET 8.
  [Qt build script](../../apps/osu-radio-qt/build.rs) уже встраивает QML и ассеты;
  внешние библиотеки и плагины требуют упаковки.

Исследован HEAD `c9f2500bad0c645d4e5e2db5dcdd9f6b712ac551`. Незавершённые изменения
поиска и БД сохраняются; релиз собирается после определения окончательного состава
исходников. [Прежний Arch-план](arch-linux-release.md) и его карточки остаются
историческим основанием; их результаты не подтверждают приёмку нового комплекта.

## 2. Согласованное техническое решение

Уточнение пользователя 2026-10-29: для T08 допускается проверка настоящего
установщика в Wine вместо обязательного установленного прогона на Windows;
факт отсутствия нативной проверки и остальная матрица T10 фиксируются отдельно.

### Форматы и зависимости

| Комплект | Способ сборки и поставки |
| --- | --- |
| Windows Setup.exe | Inno Setup; нативная сборка MSVC x64, динамический Qt, self-contained helper .NET 10, необходимые MSVC DLL внутри комплекта. Установка без скачивания runtime. |
| `osu-radio-git` | Полная основная ветка Git; сборка в Arch с системными Qt и .NET 10. |
| `osu-radio-bin` | Отдельный бинарный архив, собранный в чистом актуальном Arch x86_64: GUI, сервер и framework-dependent helper; системные Qt и .NET 10, без SDK при установке. |

Windows Setup и архив для Arch собираются из одного commit. Linux-сборка
использует системный Qt Arch; Ubuntu 22.04, `aqtinstall`, Qt 6.8.3 и инструменты
AppImage больше не являются обязательными входами. Это не меняет минимальную
версию Qt в исходниках и не требует перехода Windows на Qt из Arch.

Для Arch фиксируются образ/состояние сборочной среды, фактические версии пакетов,
Rust/.NET/Qt, параметры и hashes. T05 формирует архив с системной раскладкой,
T07 проверяет его через `-bin` в чистой runtime-среде и объявляет зависимости.
Системные библиотеки Qt/.NET в этот архив не включаются. Совместимость с другими
дистрибутивами не обещается. Существующие средства `packaging/linux/` и Arch-рецепт
адаптированы для Arch в T05; старые Ubuntu inputs сохранены как история.

### Запуск, пути и данные

- На Windows SQLite по умолчанию располагается в
  `%LOCALAPPDATA%\osu-radio\osu-radio.db`. Требуется абсолютный пользовательский
  путь; отсутствие подходящего каталога или ошибка создания дают явную ошибку
  запуска. Явный `SQLITE_DATABASE_URL` сохраняет приоритет.
- Linux сохраняет действующие XDG/HOME правила. Клиент передаёт
  `OSU_RADIO_SKIP_DOTENV=1` дочернему серверу на Linux и Windows. Самостоятельный
  сервер сохраняет прежнюю загрузку `.env`.
- Поиск helper: runtime `OSU_LAZER_REALM_PARSER_PATH` → установленный путь
  относительно исполняемого backend/CLI → существующий build-time путь.
  Ошибочный явный override не подменяется другим helper. Этот порядок согласован
  пользователем.
- Linux использует `../lib/osu-radio/osu-lazer-realm-parser` относительно
  бинарника; Windows — `helper/osu-lazer-realm-parser.exe`.
- Пакетные сборки встраивают относительный установленный путь, разрешаемый от
  исполняемого файла. Абсолютный build-time путь остаётся для разработки.
  Поставка не зависит от build tree или cwd.
- QSettings сохраняет организацию, приложение и существующие ключи. Миграции,
  запрет автоматического reset, временное аудио и владение процессами сохраняются.

HTTP, NDJSON и публичные Rust-интерфейсы не меняются. Новые правила остаются в
существующих владельцах: серверная конфигурация, client supervision и scanner.
Сохраняются [утверждённая архитектура](../agent/architecture.md) и
[контракты БД](../agent/database.md).

### Версия и релизный источник

Пользователь выбрал **перенос существующего `v0.1.0-alpha`** на окончательный
commit. Версия приложений и релиза остаётся `0.1.0-alpha`.

Перед переносом фиксируются старый commit
`bf941c29b2e69fa73aca6c1c6a7c1643f3a7f3f9`, прежние контрольные суммы и пояснение
о замене исходников. После переноса проверяется соответствие тега, архива и
исходников сборки.

Для `-bin` `pkgrel` выбирает T07 по `vercmp` с уже устанавливавшимся локальным
`osu-radio` `0.1.0alpha-1`. Версия `-git` имеет вид
`0.1.0alpha.r<число-коммитов>.g<hash>`; история клонируется полностью. Все варианты
предоставляют `osu-radio`, конфликтуют между собой и устанавливают прежние команды.

Выбор способа привязки исходников не означает выполненного переноса тега или
разрешения на commit/push и публикацию GitHub Release/AUR. Эти действия не входят
в подготовку данного плана.

## 3. Крупные этапы реализации

1. **Переход helper на .NET 10.** Обновить оба C# проекта, build script,
   диагностику, CI, рецепты и инструкции. Сохранить Realm `20.1.0`; использовать
   обычную публикацию каталогом без trimming, AOT и single-file. Подтвердить
   framework-dependent и self-contained варианты на целевых ОС. Эти режимы
   различаются наличием runtime в publish-каталоге.
   [Документация .NET](https://learn.microsoft.com/en-us/dotnet/core/deploying/).

2. **Установленный запуск.** Реализовать Windows SQLite fallback, расширить
   отключение `.env`, добавить согласованный поиск helper. Переиспользовать
   существующие subprocess-тесты. Установленные приложения и дочерние процессы
   Windows запускаются без лишних консольных окон, с сохранением захвата
   stdout/stderr.

3. **Бинарный комплект для Arch.** Адаптировать существующие средства T05
   для сборки в чистом актуальном Arch с системным Qt и .NET 10. Сохранить
   Linux-архив с раскладкой `usr/bin`, `usr/lib/osu-radio`, desktop entry,
   иконкой, лицензиями и сведениями о сборке. Проверить runtime-зависимости,
   относительный helper и запуск без SDK/исходников. Исторический Ubuntu-архив
   не использовать как доказательство выполнения обновлённой T05.

4. **Arch-варианты.** Обновить существующий рецепт как основу `-git` и добавить `-bin`.
   Все используют одинаковые команды и каталоги данных. Для `-git`
   нужны SDK сборки; для `-bin` — только runtime-зависимости. `.SRCINFO` получать
   через `makepkg --printsrcinfo`, дополнительные файлы проверять SHA-256.

5. **Windows-комплект.** Разместить GUI и сервер рядом, helper — отдельным
   подкаталогом. Выполнить `windeployqt --qmldir`, затем проверить дополнительные
   зависимости сервера и Realm.
   [Документация Qt](https://doc.qt.io/qt-6.8/windows-deployment.html).
   Inno Setup использует постоянный AppId, установку текущему пользователю по
   умолчанию и выбор всех пользователей с повышением прав. MSVC runtime
   поставляется локальными разрешёнными DLL, включая каталог helper. Обновление
   заменяет компоненты приложения; удаление сохраняет пользовательские данные
   и QSettings.

6. **Иконки, CI и релизный комплект.** Из существующего `lazer.png` подготовить
   ICO и Linux PNG; включить иконку в Windows EXE/Setup, меню, список программ,
   Arch desktop entry. Сохранить provenance. CI собирает выбранный SHA
   на Windows и в Arch-среде, фиксирует инструменты и выпускает артефакты
   проверки без автоматической публикации. После сборки формируются окончательные
   рецепты, `.SRCINFO`, SHA-256 и manifest с commit, версиями и параметрами сборки.
   Генерация выполняется в release staging, чтобы checksum бинарника не создавал
   цикл с commit исходников.

Этапы Linux/Windows зависят от перехода helper и правил установленного запуска.
Arch `-bin` зависит от Linux-архива. Финальные рецепты требуют окончательной
привязки тега и проверенного архива исходников; предварительные сборки не
выдаются за финальную приёмку. Итоговый CI-комплект зависит от всех форматов.

Лицензионный комплект сверяется отдельно для каждой поставки, включая Qt, .NET
и native-компоненты. Для поставляемого Qt сохраняются соответствующие исходники
и сведения о замене динамических библиотек.
[Требования Qt](https://www.qt.io/faq/qt-open-source-licensing).

## 4. Проверка результата

Основные риски: неверные пути после установки, неполный runtime-комплект, потеря
данных при обновлении и несовместимость Realm. Новые проверки ограничиваются
этими рисками.

| Область | Минимально необходимые проверки |
| --- | --- |
| Конфигурация и helper | Windows-пути с пробелами/кириллицей, отсутствующий/неподходящий LOCALAPPDATA, ошибка создания каталога, приоритет явного URL; порядок поиска helper, ошибочный override, перенос комплекта и независимость от cwd. |
| Совместимость | Существующие Linux XDG, standalone `.env`, remote-сессия, server readiness и shutdown; existing migration fixtures и отказ без reset при несовместимой БД. |
| .NET 10 | Существующие real-helper тесты и NDJSON-контракт, неизменность входных файлов, нативные Windows/Linux helper; затем реальная lazer-библиотека из установленного комплекта. |
| Упаковка | Чистые сборки Arch, актуальные `.SRCINFO`, checksums, зависимости и конфликты; отсутствие SDK у `-bin`; Windows без установленных Qt/.NET/SDK. |
| Пользовательский сценарий | Каждый вариант: запуск → отдельный импорт stable и lazer → слышимый звук → закрытие → повторный запуск. Проверить restart, update, reinstall, uninstall/reinstall и смену Arch-варианта с сохранением библиотеки, плейлиста и настроек. |

Матрица приёмки: Windows 10 22H2 и LTSC 2021, Windows 11; актуальный Arch x86_64. Windows 10 22H2/LTSC 2021 выбраны
пользователем; работа обычной Windows 10 подтверждается собственной приёмкой,
отдельно от официальной поддержки Microsoft.
[Матрица .NET 10](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md).
Точные сборки ОС фиксируются в результатах. Проверяются доступные Arch X11/Wayland
сессии, удаление build tree, иконки и read-only доступ к выбранным
osu!-источникам. Discovery ограничивается явно заданными тестовыми корнями.

Для приёмки нужны чистые Windows-профили/VM, чистое Arch-окружение, выбранные
runtime-зависимости Arch, тестовые stable/lazer-библиотеки и нативная desktop-сессия
с реальным аудиовыходом. Рабочая БД разработчика не используется. Наличие
локальных .NET SDK и Qt не подтверждает доступность всей этой матрицы;
подготовка недостающих сред входит в этап проверки комплектов.

Rust/Qt проверки выполняются по [матрице проекта](../agent/development.md#verification-matrix):
затронутые тесты, client mock off/on, сервер docs on/off, scoped Clippy,
форматирование, Qt probes и QML lint при изменении Qt-кода. Socket-тесты
запускаются в разрешённом окружении. Backend features не объединяются через
`--all-features`.

Переиспользуются проверки
[конфигурации](../../apps/osu-radio-server/src/config/tests.rs),
[запуска сервера](../../apps/osu-radio-server/tests/startup.rs),
[helper build script](../../crates/radio-scanner/tests/test_build_helper.py),
[Realm и NDJSON](../../crates/radio-scanner/src/lazer/tests.rs) и существующие
проверки supervisor. Уровень установленного комплекта покрывает взаимодействие
Qt/runtime/launcher/helper; offscreen-проверки не заменяют native GUI и звук.

Обновляются затронутые agent guides и таблица R1–R9 в спецификации, отдельно
отмечая выполненные проверки и неподтверждённые среды. В спецификации фиксируются
согласованные Windows-матрица и решение по тегу; требования не сужаются молча.

## 5. Готовность и передача

Существенные решения согласованы; существующие карточки обновлены под новый
объём. T05 подготовила Arch-кандидат для T07; ограничение Qt-прогона записано
в её отчёте. Следующие карточки выбирает пользователь; T08 для Windows независима.
Несовместимость Realm/.NET 10 или целевых Windows/Arch блокирует соответствующее
требование и требует решения пользователя. Приоритет Windows не требует ждать T05/T07.

При планировании выполнена ограниченная Linux-проба: текущие helper и генератор
опубликованы как `net10.0/linux-x64`, self-contained, с runtime `10.0.13` и Realm
`20.1.0`. Три синтетических Realm-файла (`full.realm`, `no-collections.realm`,
`metadata.realm`) прочитаны как NDJSON; SHA-256 входных файлов сохранились.
Проба использовала временные копии в `/tmp`, без изменения исходников проекта.
Полный набор Rust real-helper тестов этой пробой не заменяется. Версия runtime
пробы не закрепляет версию финального релизного runtime.

Context7 во время проработки вернул ошибку месячной квоты; upstream-решения
проверены по приведённым официальным источникам. Квоту можно восстановить через
`npx ctx7@latest login` или `CONTEXT7_API_KEY`.

Декомпозиция через `$impl-tasks` подготовлена 2026-10-27, см. разделы 6–8.
Код продукта, Git-теги и публикации при этом не менялись; нативные установщики,
GUI, реальные библиотеки и звук не проверены. Основной остающийся риск —
переносимость полного установленного комплекта.

## 7. Внешние входы и границы готовности

1. **Окончательный источник.** Текущие незавершённые изменения поиска/БД не
   присваиваются этой задаче и не откатываются. Для окончательной сборки нужен
   чистый зафиксированный commit с выбранным пользователем составом изменений.
   Подготовка карточек и их выполнение сами по себе не разрешают commit/push,
   перенос тега, GitHub Release или AUR.
2. **Тег и контрольные суммы.** Выбор перенести `v0.1.0-alpha` уже согласован
   в разделе 2. Сам перенос выполняется только по отдельному поручению.
   T07 может проверить рецепты на локальном candidate-архиве; T09 может
   реализовать CI и собрать candidate по SHA до переноса. Для окончательного
   комплекта T09 нужен реально перенесённый тег, соответствующий архив и их
   проверенные идентификаторы. Отсутствие этого входа оставляет финализацию
   незавершённой, но не требует заново обсуждать выбранный способ привязки.
   Старый commit и checksums сохраняются в пояснении замены; новые рецепты,
   `.SRCINFO` и manifest формируются в staging вне исходного commit.
3. **Среды.** Нативные Windows/Linux .NET-проверки нужны уже T01; чистый
   Arch — T05/T07; Windows MSVC/Qt/Inno Setup — T08. T10 проверяет чистые
   профили/VM и доступные desktop-сессии с аудиовыходом по матрице раздела 4.
   Отсутствующая среда — непроверенный критерий, не успех. Ubuntu не требуется.
4. **Сохранение свидетельств.** Старый отчёт T05 и Ubuntu inputs сохранены;
   Arch-путь реализован и проверен с ограничениями Qt-прогона в отчёте T05. Падения Qt 6.8.3 не объявляются исправленными,
   но не требуют отдельного Ubuntu-прогона ради этого релиза. Если дефект
   воспроизводится на целевых Windows/Arch, он относится к их приёмке.
5. **Существенные препятствия.** Несовместимость Realm/.NET 10 или необходимость
   менять архитектурный контракт возвращаются в `$impl-plan`. Переход на .NET 8,
   исключение целевой ОС или изменение данных не являются локальными обходами.

## 8. Сверка декомпозиции и передача

При декомпозиции сверены текущие startup/config, supervision и scanner entry
points, оба C# проекта, реальные Realm-фикстуры, CI, Qt resources, Arch-рецепт,
версии и provenance. HEAD остаётся указанным в разделе 1; локальный тег
разрешается в прежний commit из раздела 2. Старые Arch-карточки не изменялись;
их исторические команды не переносятся без проверки: например, корневого
каталога `tests/` сейчас нет.

Проверка этой стадии ограничена документами: покрытие R1–R9, ацикличность
зависимостей, локальные ссылки, наличие исходных символов и применимость
указанных существующих test targets. Сборки, тесты продукта и приёмка
не запускались. Новые проверки будущей реализации привязаны к рискам путей,
runtime/Realm, установленного запуска и потери данных, без нового общего
тестового каркаса.

Для старта выбранной задачи: `$impl-exec, выполни карточку
docs/impl/first-release-packaging/T08.md; запиши результаты проверок`.
Это пример поручения, а не запуск следующего скилла. В отчётах карточек
разделяются реализация, автоматизированные проверки и пользовательская приёмка.
После T10 существенные результаты и ограничения переносятся в спецификацию;
план и карточки сейчас не удаляются.
