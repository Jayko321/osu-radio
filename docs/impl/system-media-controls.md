# План реализации: системное управление воспроизведением

Статус: T01–T07 реализованы; доступные финальные проверки выполнены. Qt suite:
2 прежних gallery crash; metadata suite имеет отдельный handoff в T07.
Linux runtime, hardware и пользовательская приёмка открыты.

## Источник и цель

Источник требований: [спецификация](../specs/system-media-controls.md), R1–R9.
Добавить автоматическое управление локальным воспроизведением через MPRIS на
Linux и SMTC на Windows, включая работу с удалённым HTTP-сервером. Системные
метаданные и команды относятся к текущему воспроизведению независимо от выделения.

## Существующий код

- [AppController и AppCommand](../../crates/osu-radio-client/src/controller.rs)
  предоставляют один цикл событий, очередь команд и подтверждаемое завершение.
  [Координатор](../../crates/osu-radio-client/src/controller/coordinator.rs)
  связывает VM, worker и фоновые интеграции; `update_discord` уже проверяет
  соответствие назначения и фактического воспроизведения.
- [PlayerViewModel](../../crates/osu-radio-client/src/view_models/player.rs)
  хранит `current_track`, назначение и `Playback` отдельно от выделения.
  `toggle_playback` и `seek_selected` зависят от выделения, поэтому напрямую
  использовать их для системного управления нельзя.
- [Playback и worker](../../crates/osu-radio-client/src/playback.rs) проверяют
  токен запуска и audio ID при перемотке. `seek_serial` изменяется после успешного
  seek. Существующий `PendingPlayback` сохраняет последовательное исполнение
  транспортных команд.
- [SettingsViewModel](../../crates/osu-radio-client/src/view_models/settings.rs)
  владеет общей и индивидуальной громкостью, сохранением, debounce и обработкой
  ошибок. `set_selected_volume` и `set_track_volume` ограничены выделенным треком;
  системному управлению нужен путь к текущему треку с теми же правилами сохранения.
- [MediaScheduler](../../crates/osu-radio-client/src/controller/media.rs) имеет
  ограничения размера, поколения, отмену и четыре параллельных конвейера. Его
  следует расширить спросом текущего воспроизведения и доставкой системному
  потребителю, сохранив подтверждение доставки Qt.
- [Qt AppBridge](../../apps/osu-radio-qt/src/app_bridge.rs) связывает GUI с
  контроллером. [Launcher](../../apps/osu-radio-qt/src/main.rs) и
  [LiveRuntime](../../apps/osu-radio-qt/src/runtime.rs) сейчас завершают runtime
  после уничтожения Qt-объектов. Для SMTC требуется отдельное отключение до
  уничтожения нативного окна.

Существующие изменения `.env`, `.gitignore`, Qt build script и frontend guide
сохранить. Серверные контракты, схема хранения и порядок очереди не меняются.

## Техническое решение

### Границы и зависимости

- **Согласовано пользователем:** создать отдельный crate
  `crates/osu-radio-media-controls`. Он содержит общий контракт, жизненный цикл
  системного подключения и платформенные адаптеры. Это изолирует нативные
  зависимости от клиента и Qt.
- `osu-radio-client` зависит от нового crate и остаётся владельцем правил
  воспроизведения, выбора текущего трека и координации. Новый crate получает
  готовые снимки и возвращает события; он не обращается к HTTP, базе, очереди
  или аудиодвижку и не зависит от клиента или Qt.
- **Согласовано пользователем:** использовать `mpris-server 0.10` на Linux и
  `windows 0.62` на Windows через зависимости соответствующей целевой ОС.
  `mpris-server` сокращает собственный протокольный код. Linux использует
  существующий Tokio runtime с включённой поддержкой Tokio у библиотеки.
  Обновить workspace и lockfile без незапрошенного обновления других зависимостей.

### Общий контракт и управление

- Снимок содержит непрозрачный ключ запуска на основе
  `current_entry_id`/`playback_token`, необязательные метаданные и длительность,
  фактический статус, позицию, `seek_serial`, эффективную громкость и доступность
  действий.
- События включают Play, Pause, PlayPause, Stop, Next, Previous,
  абсолютную/относительную перемотку и изменение внутренней громкости.
  Добавить подключение, публикацию снимка и подтверждаемое отключение интеграции
  в публичный фасад `AppController`; системные события идут в его существующий
  цикл.
- Публиковать последнее состояние через канал снимков: медленный системный API
  не задерживает контроллер и не накапливает позиции. События команд поступают
  отдельно и исполняются последовательно.
- Play использует существующий `Play { audio_source_id: None }`: возобновляет
  или запускает очередь независимо от выделения. Пустая очередь остаётся без
  действия. PlayPause выбирает Pause/Resume по текущему воспроизведению; при
  загрузке или ожидании проверки учитывает режим текущего назначения.
- Остальные транспортные команды используют существующую очередь исполнения
  и её правила. Доступность вычисляет клиент; недоступные события безопасно
  игнорируются.
- Системная перемотка получает ключ запуска при приёме события. Контроллер
  проверяет его перед отправкой worker, worker сохраняет проверку токена и
  audio ID. Путь GUI через выделение сохраняется.
- На Linux изменение громкости в индивидуальном режиме адресует текущий трек,
  в общем — общий уровень. Переиспользовать сохранение, debounce и обработку
  ошибок. Выделение B не меняет адресата A и само по себе не меняет громкость A.
- Публикация использует согласованные назначение и worker. Загрузка нового
  трека не заимствует Playing или позицию предыдущего запуска. Название и
  исполнитель учитывают Unicode-предпочтения; отсутствующие значения передаются
  как отсутствующие, без UI-заглушек.

### Обложки

- **Согласовано пользователем:** передавать загруженные клиентом байты.
  Добавить текущий трек в спрос `MediaScheduler`, даже если его нет среди видимых
  строк. Системный потребитель использует результат существующей загрузки,
  сохраняя её лимиты, отмену и подтверждение доставки Qt.
- Новый crate хранит временный файл только текущей обложки. Результаты проверяются
  по запуску, cover ID и поколению. Qt сохраняет владение декодированными
  изображениями и кэшем GUI.
- При смене трека старая обложка очищается сразу. Ошибка загрузки или подготовки
  обложки оставляет остальные данные и управление работоспособными.

### Платформенные адаптеры и завершение

- Linux: реализовать Root/Player через `mpris-server::Server`, отдельное имя
  экземпляра, корректный `TrackId`, уведомления об изменениях метаданных, статуса,
  громкости и возможностей. `Seeked` отправлять после подтверждённого изменения
  позиции; обычные тики позиции не оформлять как `PropertiesChanged`. Соблюсти
  правила абсолютной и относительной перемотки MPRIS. Не экспортировать
  TrackList/Playlists и не добавлять новые shuffle/repeat или OpenUri.
- Windows: получить SMTC через `GetForWindow` для HWND главного live-окна;
  публиковать метаданные, доступность кнопок и timeline. Нативные операции
  выполнять вне цикла контроллера; callbacks только передают события.
  Системный микшер остаётся независимым от внутренней громкости.
- **Согласованное уточнение R4:** SMTC не передаёт идентификатор трека.
  Защита начинается при получении callback; действие, доставленное самой ОС
  уже после смены трека, невозможно распознать как старое.
- Qt автоматически подключает интеграцию после создания live-окна. Перед
  уничтожением нативного окна подтверждённо отключает её; окончательное
  завершение runtime сохраняет существующий порядок. Галерея подключения
  не создаёт. Qt-типы и `image://` URL не пересекают границу клиента.
- Отключение идемпотентно: запрещает новые события, удаляет обработчики,
  освобождает системную сессию и временные файлы. Его вызывает и штатное
  завершение контроллера, включая повтор после раннего отключения Qt.
- **Согласованная политика ошибок:** фатальная ошибка системного API отключает
  интеграцию до следующего запуска с диагностикой. Автоматических повторов нет;
  музыка и GUI продолжают работать. Ошибка отдельной обложки не является
  фатальной ошибкой всей интеграции.

Опорная документация, сверенная при подготовке:
[MPRIS Player](https://specifications.freedesktop.org/mpris/latest/Player_Interface.html),
[mpris-server и Tokio](https://docs.rs/crate/mpris-server/0.10.0/source/Cargo.toml),
[SMTC](https://learn.microsoft.com/en-us/uwp/api/windows.media.systemmediatransportcontrols),
[GetForWindow](https://learn.microsoft.com/en-us/windows/win32/api/systemmediatransportcontrolsinterop/nf-systemmediatransportcontrolsinterop-isystemmediatransportcontrolsinterop-getforwindow),
[событие перемотки SMTC](https://learn.microsoft.com/en-us/uwp/api/windows.media.playbackpositionchangerequestedeventargs),
[QWindow::winId](https://doc.qt.io/qt-6.8/qwindow.html#winId).
Context7 использован для MPRIS, Windows bindings, Qt и поддерживающего D-Bus API;
документация `mpris-server` дополнительно проверена по источникам библиотеки.

## Крупные этапы

1. Добавить новый crate, общий контракт и подключения в workspace; подготовить
   платформенные преобразования данных и событий.
2. Подключить контракт к `AppController` и существующим владельцам
   player/settings/media. Реализовать управление текущим запуском, публикацию
   снимков и передачу обложки.
3. Реализовать MPRIS и SMTC, затем связать live-окно Qt с подключением и
   подтверждаемым отключением. Этот этап зависит от общего контракта и
   клиентского пути событий.
4. Выполнить проверки и обновить затронутые
   [architecture](../agent/architecture.md), [frontend](../agent/frontend.md) и
   [development](../agent/development.md) guides, отделяя реализацию от
   выполненной нативной приёмки.

## Проверка результата

Изменяемое поведение — дополнительный системный вход к текущему воспроизведению
и публикация его состояния. Основные риски — адресация выделенного трека,
устаревший seek, неверные метаданные и оставшиеся обработчики после выхода.

Основной уровень общих правил — клиентские тесты с fake worker. Расширять
существующие фикстуры треков, назначений и очереди в
[controller tests](../../crates/osu-radio-client/src/controller/view_model_tests.rs),
[playback tests](../../crates/osu-radio-client/src/playback.rs) и
[volume tests](../../crates/osu-radio-client/src/view_models/volume/tests.rs).
Они уже проверяют независимость выделения, token-bound seek, громкость и
shutdown flush, но не новый системный вход или подключение нативных API.

| Риск и требования | Минимальная дополнительная проверка и результат |
| --- | --- |
| Адресация выделенного трека — R2, R5 | Играет A, выбран B: системные транспорт, seek и индивидуальная громкость адресуют A. Привязку выбора из библиотеки и плейлиста проверить отдельно, без повторения всей матрицы. |
| Неверная доступность или статус — R2, R3 | Общая матрица: пустая очередь, Playing, Paused, Stopped, загрузка, ожидание проверки, ошибка worker и отсутствие следующего/предыдущего элемента. Опубликованные возможности и команды согласованы с клиентом. |
| Устаревшая перемотка — R4 | Смена запуска между callback и исполнением, включая повтор того же audio ID: запрос отбрасывается. Успешный seek обновляет позицию и `seek_serial`. |
| Неверная громкость — R4, R5 | В индивидуальном режиме системная правка меняет A при выбранном B, в общем — общий уровень. Переиспользовать существующую проверку сохранения; не повторять её матрицу для каждого системного входа. |
| Устаревшие метаданные или обложка — R3 | Смена трека, поздний ответ, отсутствие обложки/длительности и пустые текстовые поля: данные предыдущего трека не остаются. Проверить получение обложки текущего трека вне видимых строк. |
| Ошибки и утечки — R6, R9 | Ошибка подключения сохраняет работу клиента; повторное отключение безопасно, поздние callbacks игнорируются, временные файлы освобождены, завершение удалённого клиента сохраняет сервер. |

Дополнительные проверки взаимодействия компонентов:

- Linux: интеграционная проверка на изолированной D-Bus-сессии — обнаружение
  сервиса, вызов команд, свойства, сигналы и исчезновение после отключения.
  Она проверяет реальный обмен, не повторяет клиентскую матрицу.
- Windows: проверки преобразований SMTC и нативный Qt smoke для HWND,
  подключения и очистки. Offscreen-проверка не считается подтверждением
  настоящего HWND. Отдельно проверить отсутствие подключения в галерее.
- Выполнить тесты нового crate, клиентские suites с `mock` выключенным и
  включённым, последовательные Qt probes, scoped Clippy и форматирование по
  [матрице проекта](../agent/development.md#verification-matrix). QML lint нужен
  при изменении QML; `--all-features` не использовать.
- Нативная приёмка на обеих ОС: треки A/B, разные и отсутствующие обложки,
  управление без фокуса, seek в обе стороны, соответствующие правила громкости
  и выход. Нужны Linux с пользовательским D-Bus, MPRIS-клиентом и системной
  панелью, Windows с SMTC и микшером, медиаклавиши и аудиовыход.
- Локальный и удалённый режимы проверяются как варианты подключения с явно
  заданными источниками и временными тестовыми данными; общую матрицу повторять
  для каждого не требуется. В удалённом режиме клиент не запускает и не
  останавливает сервер.

Итоговая приёмка использует результаты общих тестов и проверок адаптеров,
проверяя соединение системного интерфейса с реальным приложением и worker.
Сборка, fake worker и D-Bus-тесты не подтверждают физический звук, системную
панель Windows или аппаратные медиаклавиши.

Выполнено при планировании: чтение спецификации, затронутого кода и guides,
проверка рабочего дерева, сверка upstream-документации. Сборка, тесты и
нативная приёмка фичи не выполнялись.

## Готовность к декомпозиции

Существенные решения согласованы: отдельный crate, выбранные зависимости,
передача байтов обложки из клиента, граница защиты SMTC и отсутствие
автоматических повторов после фатальной ошибки интеграции. Открытых вопросов
для декомпозиции нет. Исходная спецификация сохраняет требования; этот документ
фиксирует способ реализации и согласованные технические ограничения.

### Параллельный порядок

```text
T01 ─┬─ T02 ─┬─ T05 ─────────────┐
     │       └────────┐          │
     ├─ T03 ─────────────────────┼─ T07
     └─ T04 ──────────┴─ T06 ────┘
```

1. Сначала выполнить T01 и передать её код и фактический контракт остальным чатам.
2. После T01 запускать **T02, T03 и T04 параллельно**. T03/T04 проверяют обмен
   через общий контракт и тестового отправителя снимков; живой клиент им не нужен.
   Это разбиение реализации адаптеров, а их общая приёмка по-прежнему зависит от клиента.
3. После T02 запускать T05. T06 можно запускать после T02 и T04, одновременно с
   T05 и ещё незавершённой T03: файлы Qt и клиентского медиаконвейера различаются.
4. После T03, T05 и T06 выполнить T07. Результаты предшественников, включая T01,
   T02 и T04, должны присутствовать в общем состоянии кода.

Порядок задаёт разрешённый параллелизм, а не требование запускать агентов.
В отдельных checkout/worktree переносить завершённые зависимости до старта
зависимой карточки; один статус в таблице не заменяет код и отчёт.

Каждый исполнитель заполняет свою карточку и меняет только свою строку состояния
в таблице, перечитав актуальную версию плана; не перезаписывает весь документ.

manifest или lockfile после T01 требует отдельной последовательной правки до

Существующие пользовательские изменения `.env`, `.gitignore`, `build.rs` и
`frontend.md` сохранять; секреты из `.env` не переносить в отчёты.

### Передача контракта T01

До старта T02/T03/T04 T01 записывает в своём отчёте пути и фактические публичные
и внутренние точки подключения со следующей семантикой:

- ключ запуска отличает повтор того же audio ID и не зависит от выделения;
- снимок содержит поля из раздела «Общий контракт и управление», в том числе
  необязательные исходные метаданные, позицию, `seek_serial` и возможности;
- команды отделены от канала последнего снимка; абсолютный seek несёт ключ,
  относительный — ключ и знаковое смещение; backend фиксирует контекст при callback;
- нативный контекст Windows содержит только платформенный дескриптор live-окна,
  без Qt-типов; Linux не требует окна; клиент не получает Qt или `image://`;
- есть единые подключение, публикация, диагностика фатального отказа и
  подтверждаемое идемпотентное отключение с запретом поздних событий;
- обложка передаётся байтами с ключом запуска, cover ID и поколением; общий
  механизм временного файла доступен обоим адаптерам и очищает старую обложку;
- диспетчер вызывает изолированные Linux/Windows-модули с одинаково закреплёнными
  входами; их первоначальный явный отказ «адаптер ещё не реализован» безопасен.

Это детализация уже принятого контракта, а не новая система плагинов. Не нужны
универсальный реестр backend, новая очередь, независимый player state или настройка.
Публичные и внутренние имена выбирает T01; зависимые карточки сверяют их с её
кодом и отчётом. Изменения поведения или архитектуры возвращаются в `$impl-plan`.

### Распределение проверок

Следующие группы уточняют общий раздел «Проверка результата», не заменяя его.

| Группа | Владелец и основной уровень | Отличаемая ошибка |
| --- | --- | --- |
| V1 | T01: общий crate, тестовый backend/получатель | Накопление снимков, поздние команды, повторный shutdown, утечка временной обложки, фатальный отказ против ошибки картинки |
| V2 | T02: client tests с fake worker и существующим HTTP fixture | Управление B вместо A, несовпадение назначения и worker, неверные возможности, устаревший seek/повтор audio ID, неправильный адресат громкости или UI-заглушки в метаданных |
| V3 | T03: преобразования MPRIS и изолированная D-Bus-сессия | Ошибки протокольного преобразования, TrackId, сигналов, единиц позиции/громкости и освобождения имени |
| V4 | T04: преобразования SMTC и Windows native harness | Ошибки HWND interop, timeline, событий, отписки и платформенного преобразования; проверка Qt-владения окном относится к V6 |
| V5 | T05: существующие media/controller tests | Нет спроса невидимого текущего трека, неверный запуск/cover ID/поколение, преждевременное освобождение Qt pipeline либо зависание доставки |
| V6 | T06: runtime tests, serial Qt probes и native Windows smoke | Не произошло автоподключение, галерея подключилась, HWND уничтожен раньше завершения отключения, изменён порядок runtime cleanup |
| V7 | T07: приложение, обе ОС и реальные системные интерфейсы | Части по отдельности проходят тесты, но live-команды, обложка, позиция, клавиши, громкость или выход вместе не работают |

Матрица команд/состояний принадлежит V2, V3/V4 проверяют перевод и реальный обмен,
V6 — привязку жизненного цикла, V7 — взаимодействие. Не повторять полную матрицу
V2 для каждой ОС, каждого UI-входа или режима сервера. Дополнительный уровень
для того же правила обосновывать отдельным риском.
