Состояние: реализовано и автоматически проверено на Linux; пользовательская приёмка не выполнялась (T12).
Источники: [спецификация](../../specs/adjustable-pitch-speed.md), R1–R8,
«Приёмка и минимальные проверки»;
[проверка результата](../adjustable-pitch-speed.md#проверка-результата).
Зависимости: T01–T10 — реализации объединены, scoped checks и ограничения переданы.
Это барьер интеграции перед реальной приёмкой T12.

## Результат

Реальный сервер с disposable БД и клиент/Qt выполняют общий сценарий без
расхождений контрактов. Руководства отражают окончательную реализацию;
каждое R1–R8 имеет фактическое evidence либо явный непроверенный критерий.

## Границы и контекст

- Владение: существующие integration probes и минимальные исправления на стыках
  после передачи всех потоков; `docs/agent/frontend.md`, architecture.md,
  нужные актуализации index.md и test-coverage.md. Сверить database/backend/
  development guides, уже обновлённые T01/T05/T10. Новые решения не утверждать
  от имени пользователя; переносить только согласованные решения плана.
- Использовать реальные server REST/NDJSON и disposable SQLite со scoped
  synthetic audio sources; worker можно подменить существующим FakeEngine
  ради детерминированного журнала параметров. Переиспользовать backend probes
  в `apps/osu-radio-qt/tests/launch_smoke.rs` и клиентские fixtures.
  Не создавать отдельное приложение/тестовую инфраструктуру.
- Проверить полный пользовательский сценарий: общий DT → individual с none
  по умолчанию → A NC 1.20/B HT → shared audio/плейлист/очередь → restart
  и remove/reimport той же идентичности → играть A/изменить B → явный Play B
  → изменение speed/pitch, pause/resume/seek → automatic next.
  Проверить согласованность сохранённого профиля, передачи до первого play,
  временной шкалы, queue token и внешнего snapshot.
- Это проверка взаимодействия, не повторение всей unit-матрицы. Сохранить
  исходные файлы и существующие данные. Только test DB/явные источники,
  никаких сбросов пользовательской БД или unscoped discovery.

## Проверка и приёмка

Сначала `cargo build -p osu-radio-server --locked`; затем opt-in real-backend
probes по [матрице](../../agent/development.md#verification-matrix), включая
`cargo test -p osu-radio-qt --test launch_smoke --locked real_backend_queue_survives_restart_and_preserves_exact_entry_actions -- --ignored --exact --test-threads=1`
на Unix. Расширить подходящий существующий probe интеграцией модов; фиксировать
что использовало реальный движок, что fake/offscreen. Запустить нужные проверки
нового сценария явно, а не полагаться на обычный suite, пропускающий ignored.

После объединения выполнить обязательную scoped regression: SQLite и свежие
PostgreSQL отдельно, server docs on/off, client mock off/on, player/native,
serial Qt и generated-import lint; scoped Clippy, `cargo fmt --check`,
`git diff --check` и `python3 -B -m unittest discover -s tests -v`.
Команды/feature flags — по development guide, без --all-features.
Достаточно одного общего прогона итогового состояния: не повторять уже
прошедшие проверки без изменений/неразрешённого риска. Сверить build evidence
Linux/Windows из T10; недостаток среды оставить открытым перед T12.

Заполнить в спецификации раздел evidence/ограничений, не меняя R1–R8;
реальную приёмку пока не отмечать выполненной. Составить короткий handoff
T12 с версиями/бинарниками, fixture sources и точными открытыми проверками.

## Отчёт о выполнении

Выполнено 2026-10-24 в основном чате, без субагентов. Linux x86_64, Rust 1.98.0,
HEAD `cf84338` + незакоммиченные изменения T01–T10; коммиты не создавались.
Пользовательские БД и источники osu! не открывались: SQLite — временные каталоги
fixture, PostgreSQL — свежий кластер с `radio_db_test_t11_*`, удалён после прогона.

### Реализация

- [real_backend.rs](../../../crates/osu-radio-client/src/playback/tests/real_backend.rs):
  общий `prepared()` вместо дублируемого setup; `drive_with(parameters)` (`drive` сохранён
  с параметрами по умолчанию); новый ignored probe
  `real_server_mods_follow_each_launch_across_restart_reimport_and_live_edits`.
  Fixture [queue_backend.py](../../../apps/osu-radio-qt/tests/fixtures/queue_backend.py)
  из T09 не менялся (индивидуальный режим, общий DT 1,30×, A = NC 1,20×, B/C без профиля).
- Probe использует **реальные** сервер, SQLite, REST, импорт/удаление/реимпорт, перезапуск
  `Session` и правило `Editor::effective` клиента; **fake** — только движок (`FakeEngine`).
  Сценарий: переключение режима не стирает наборы → B = HT 0,75 → A из очереди стартует
  с `{1.2, pitch}` до первого `play` → правка B при звучащем A не меняет assignment A,
  queue revision/token → живая правка A (1,5×, затем pitch) сохраняет token/источник/позицию/
  паузу (без перезагрузки и нового `play`) → resume и seek → перезапуск → remove/reimport той же
  идентичности возвращает профили, общее аудио двух сложностей имеет один профиль →
  явный Play B стартует с `{0.6}` → автоматический next: C без профиля получает `{1.0, false}`
  (общий 1,3× не наследуется), затем A `{1.5, pitch}`; параметры предыдущего запуска не переносятся.
- Мутация: `Editor::effective` временно возвращала общий профиль вместо 1× — probe упал
  на C (`1.3` вместо `1.0`); файл восстановлен из копии, побайтово сверен.
- Руководства: [frontend](../../agent/frontend.md#adjustable-speed-and-pitch) (новый раздел и
  указатели в playback/Discord/system media), [architecture](../../agent/architecture.md)
  (владелец SettingsVM, граница player, раздел согласованных решений, evidence),
  [index](../../agent/index.md), [development](../../agent/development.md) (строки матрицы и
  команда probe), [test-coverage](../../agent/test-coverage.md) (раздел T11). Database/backend/
  development, обновлённые T01/T05/T10, сверены с кодом и отчётами: расхождений нет.
  Ссылки/якоря изменённых guides проверены; единственная битая ссылка
  (`system-media-controls/T07.md` в development.md) есть уже в HEAD и не менялась.
- Спецификация: раздел «Состояние и свидетельства» заполнен; R1–R8 не менялись.

- Реальный звук, слышимые артефакты DSP при смене параметров/seek, качество на музыке.
- Probe не прогоняет настоящий DSP, `PlayerPresentation`/`system_snapshot`/Discord через
  реальный сервер и Qt-слой: шкала времени, rate и Discord подтверждены только unit-тестами
  T07/T08 с fake backend; связующее звено — `Snapshot.parameters` из worker (проверено в probe).
- Нативные F1/D/E, живой drag по звучащему треку, hit-test/фокус/GPU, реальные
  MPRIS-панель, SMTC, Discord; Windows сборка и запуск; hosted CI; PostgreSQL HTTP runtime
  (только compile/lint обоих router, PostgreSQL runtime — слои db/services).
- Расхождений со спецификацией, планом и архитектурой не обнаружено; решений от имени
  пользователя не принималось. Реализация и автоматическая проверка — выполнены;
  **пользовательская приёмка не выполнена.**
