# Arch Linux: релиз osu! radio 0.1.0-alpha

Статус: технический план согласован; T01–T05 выполнены в области карточек.
T05 проверила опубликованный источник, clean Arch chroot и установленный пакет
без исходников/SDK; замечание partial RELRO native Realm разобрано в отчёте.
Пользовательская приёмка KDE/библиотек/звука остаётся T06.
Дата согласования: 2026-10-17.
Исследованное состояние репозитория: `48d2c0997ea7d6125d4bf421d692e499c0c3ab0d`.
Результаты реализации — в отчётах карточек; приёмка релиза не подтверждена.

## 1. Источник, цель и существующие механизмы

Источник: [docs/specs/arch-linux-release.md](../specs/arch-linux-release.md).
Результат: пакет `osu-radio`, обеспечивающий путь «собрал → установил → открыл
из меню KDE → добавил osu! → слушаешь».

Основание решения:

- [ServerConfig::from_env](../../apps/osu-radio-server/src/config.rs)
  автоматически загружает `.env` и требует URL базы.
- [EmbeddedServer](../../crates/osu-radio-client/src/server.rs) уже находит сервер
  рядом с приложением или в PATH, запускает его на свободном локальном порту
  и управляет завершением.
- [Build script сканера](../../crates/radio-scanner/build.rs) позволяет встроить
  установленный путь помощника через `OSU_LAZER_REALM_PARSER_PATH`. Изменять поиск
  помощника в сканере не требуется.
- [Qt build.rs](../../apps/osu-radio-qt/build.rs) уже встраивает QML и ассеты.
  [SettingsPanel](../../apps/osu-radio-qt/qml/SettingsPanel.qml) подходит для
  сведений о приложении; [runtime.h](../../apps/osu-radio-qt/src/runtime.h)
  использует QSettings с установленными ключами.
- [Соединение SQLite](../../crates/radio-db/src/connection.rs) уже создаёт файл
  базы, а [AppState::connect](../../apps/osu-radio-server/src/state.rs)
  выполняет миграции. Добавить нужно выбор стандартного пути и создание
  родительского каталога.

Сохраняются [утверждённая архитектура](../agent/architecture.md), существующие
границы компонентов и пользовательские сценарии спецификации. На момент
исследования в рабочем дереве были изменения `.serena/project.yml`
и неотслеживаемая спецификация; их сохранять.

## 2. Техническое решение

### Согласованные решения

| Решение | Причина и следствие | Статус |
| --- | --- | --- |
| Помощник lazer без встроенного .NET, с системным `dotnet-runtime-8.0` | Меньше комплект поставки; runtime обновляется через pacman. | Выбрано пользователем. |
| Rust из `rust-toolchain.toml` через rustup | Используется закреплённый toolchain проекта. Конфликт пакетов Arch `rustup` и `rust` отражается в инструкции. | Выбрано пользователем. |
| Отключение поиска `.env` у сервера, запущенного клиентом | Обычный запуск приложения не зависит от `.env` текущего каталога; самостоятельный сервер сохраняет нынешнее поведение. | Выбрано пользователем. |

Остальные детали ниже конкретизируют выбранный подход в существующих границах.

### Запуск и пользовательские данные

На Linux `EmbeddedServer` передаёт дочернему процессу
`OSU_RADIO_SKIP_DOTENV=1`. Сервер при этом значении пропускает
`dotenvy::dotenv()`. Остальные режимы загрузки `.env`, включая ошибки чтения
и приоритет переменных процесса, сохраняются.

Для Linux-сборки с SQLite при отсутствии `SQLITE_DATABASE_URL` использовать:

```text
$XDG_DATA_HOME/osu-radio/osu-radio.db
```

Если `XDG_DATA_HOME` отсутствует, пуст или относителен, использовать
`$HOME/.local/share/osu-radio/osu-radio.db`. Создавать каталог автоматически;
ошибки определения пути и записи передавать через существующую обработку ошибок.
Явный URL базы сохраняет приоритет. Правила абсолютных XDG-путей следуют
[спецификации XDG](https://specifications.freedesktop.org/basedir/latest/).

Выбор пути остаётся в серверной конфигурации. Миграции и отсутствие
автоматического сброса сохраняются. PostgreSQL продолжает требовать свой URL;
новую схему каталогов Windows эта задача не вводит.

QSettings сохраняет организацию, приложение и существующие ключи. Его текущий
механизм учитывает `XDG_CONFIG_HOME`. Для кэша Qt используются стандартные
пользовательские пути; временное аудио сохраняет существующий механизм очистки.
Новые журналы и хранилище настроек не добавляются.

### Упаковка

Комплект размещается в `packaging/arch/`: `PKGBUILD`, `.SRCINFO`,
`osu-radio.desktop`, инструкция и необходимые материалы лицензий.

По умолчанию выбрать `arch=('x86_64')`, `pkgver=0.1.0alpha`, `pkgrel=1`.
Источник — архив GitHub тега `v0.1.0-alpha` с SHA-256 из проекта
`https://github.com/Jayko321/osu-radio`. Версии Qt-приложения и сервера привести
к `0.1.0-alpha`, согласованно обновив Cargo.lock.

Состав установки:

| Путь | Содержимое |
| --- | --- |
| `/usr/bin/osu-radio-qt` | Qt-приложение |
| `/usr/bin/osu-radio` | Символическая ссылка на Qt-приложение |
| `/usr/bin/osu-radio-server` | Локальный сервер |
| `/usr/lib/osu-radio/` | Полный publish-каталог помощника lazer |
| `/usr/share/applications/osu-radio.desktop` | Пункт меню |
| `/usr/share/licenses/osu-radio/` | Лицензии и обязательные уведомления |

Помощник публиковать для `linux-x64` через
`dotnet publish --self-contained false`, сохраняя DLL, runtimeconfig, deps
и нативную библиотеку Realm. Такой способ поддержан
[документацией .NET](https://github.com/dotnet/docs/blob/main/docs/core/deploying/index.md).

При production-сборке Rust задавать:

```text
OSU_LAZER_REALM_PARSER_PATH=/usr/lib/osu-radio/osu-lazer-realm-parser
```

Это встраивает установленный путь и отключает повторную сборку помощника
из Rust. Runtime override помощника сохраняется.

Зависимости упаковки:

- Сборка: `rustup`, `dotnet-sdk-8.0`, `lld`, `pkgconf`; исходная система содержит
  `base-devel`.
- Запуск: `glibc`, `libgcc`, `libstdc++`, `alsa-lib`, `qt6-base>=6.8`,
  `qt6-declarative>=6.8`, `qt6-svg`, `qt6-wayland`, `dotnet-runtime-8.0`,
  `xdg-desktop-portal` и `xdg-desktop-portal-impl`.
- Для KDE инструкция указывает реализацию портала `xdg-desktop-portal-kde`:
  существующий выбор папки через `rfd` использует портал.
- `optdepends`: `osu` для stable и `osu-lazer-bin` для lazer. Имена проверены
  через публичный AUR RPC 2026-10-17; пакеты игры не становятся обязательными.

SDK и runtime .NET 8 присутствуют в официальном репозитории Arch:
[dotnet-sdk-8.0](https://archlinux.org/packages/extra/x86_64/dotnet-sdk-8.0/),
[dotnet-runtime-8.0](https://archlinux.org/packages/extra/x86_64/dotnet-runtime-8.0/).
Перед выпуском повторно сверить метаданные зависимостей и результат анализа
готового пакета.

Сборочные каталоги Cargo, rustup и .NET размещать внутри рабочего каталога
упаковки. Использовать Cargo.lock и `--locked`; явно выбирать LLD и исключить
зависимость от личных настроек разработчика. Проверки с помощником из сборочного
дерева выполнять в отдельном Cargo target-каталоге, чтобы этот путь не попал
в поставляемые бинарники. Сервер собирается с SQLite; несовместимые backend
features не объединяются.

`.desktop` содержит `Name=osu! radio`, `Exec=/usr/bin/osu-radio`,
`Terminal=false`, `Categories=AudioVideo;Audio;Player;`. Поля `Icon` и `Path`
отсутствуют.

Инструкция описывает зависимости, конфликт `rustup`/`rust`, первую загрузку
toolchain и зависимостей, сборку и установку через `makepkg -si`, обновление
пакета и расположение пользовательских данных. Установочные операции не меняют
пользовательскую БД и настройки.

## 3. Крупные этапы

1. Подготовить SQLite fallback и отключение `.env` у дочернего сервера.
   Обновить затронутые тестовые окружения.
2. Согласовать версии, добавить About и комплект лицензий.
3. Подготовить упаковку, установленные пути, метаданные и инструкцию
   сборки/обновления. Этот этап зависит от первых двух.
4. Проверить чистую сборку и установленное приложение. Обновить затронутые
   разделы [backend](../agent/backend.md), [frontend](../agent/frontend.md),
   [development](../agent/development.md), при необходимости
   [database](../agent/database.md) и инвентарь
   [проверок](../agent/test-coverage.md).

Это крупные этапы; подробные карточки создаёт отдельный `$impl-tasks`.

## 4. Проверка результата

- **R3/R9:** изолированные subprocess-тесты стандартного пути БД,
  переопределённого XDG, пустого/относительного XDG, явного URL, ошибок каталога
  и повторного открытия базы.
- **Совместимость запуска:** дочерний сервер игнорирует корректный
  и повреждённый `.env` в произвольном cwd; самостоятельный сервер сохраняет
  прежние проверки `.env`. Remote-сессия продолжает обходиться без локального
  сервера.
- **Изоляция тестов:** обновить server startup/config tests, client
  embedded-server test, Qt real-backend probes и общую
  [queue_backend.py](../../apps/osu-radio-qt/tests/fixtures/queue_backend.py).
  Сейчас часть из них получает тестовую БД через `.env`; после изменения каждый
  процесс должен явно получать приватные пути и настройки.
- **R10:** Qt-проба проверяет версию, лицензию, ссылку и поиск About.
  Выполнить QML lint и затронутые Qt/client проверки.
- **R1/R2/R5/R6/R8:** собрать пакет в чистом Arch chroot, проверить `.SRCINFO`,
  `.desktop`, зависимости и лицензии. После установки удалить исходники
  и сборочный каталог; проверить сервер и настоящий помощник lazer.
- **R4/R7/R9:** в реальной KDE-сессии пройти импорт stable и lazer, включая
  ручную установку osu!, воспроизведение через аудиовыход, закрытие, повторный
  запуск, обновление и переустановку с сохранением данных. Проверить сохранность
  исходных файлов osu! и очистку временного аудио после нормального завершения.

Rust-проверки выполнять по [матрице проекта](../agent/development.md#verification-matrix):
сервер с docs и без них, client mock off/on, затронутые тесты и Clippy.
Backend features проверять раздельно; Cargo `--all-features` не использовать.

Для приёмки нужны чистый Arch chroot, отдельное окружение установки, реальная
KDE-сессия с аудиовыходом и тестовые библиотеки stable/lazer с явно заданными
путями. Рабочая БД разработчика не используется. `devtools` для chroot в текущем
окружении исследования не обнаружен; подготовка приёмочного окружения входит
в соответствующий этап проверки.

## 5. Исходные условия декомпозиции

Существенные технические решения согласованы. Декомпозиция выполнена 2026-10-17
по следующим документам:

- спецификацию `docs/specs/arch-linux-release.md`;
- этот план `docs/impl/arch-linux-release.md`.

Тега релиза пока нет. Финальный checksum и проверка сборки из опубликованного
тега зависят от его появления; публикация тега остаётся отдельным поручением.
Предварительная сборка из локального тега не закрывает эту часть R8.

В ходе подготовки плана изучены исходники, тестовые окружения, локальные
метаданные пакетов и документация .NET, Qt, rustup, Arch и XDG. Код продукта
не изменялся. Чистая сборка, установка, KDE и реальный звук не проверялись;
ни один критерий приёмки релиза не объявляется выполненным.

### Порядок, области изменения и точка синхронизации

- Основной поток: **T01 → T02**. Их порядок нужен из-за общих
  `apps/osu-radio-qt/tests/launch_smoke.rs` и `docs/agent/development.md`.
- Независимый поток: **T03**. Его область — корневой текст лицензии,
  материалы атрибуции и `packaging/arch/licenses/`; он не меняет manifests,
  Cargo.lock, код приложения или руководства первого потока.
- **Точка синхронизации перед T04:** приняты результаты T01, T02 и T03.
  Исполнитель сверяет итоговые версии и фактический состав лицензий, а затем
  создаёт остальные файлы упаковки. Параллельная работа здесь только разрешена,
  агенты автоматически не запускаются.
- После синхронизации: **T04 → T05 → T06**. T05 может начать подготовку
  окружения после T04, но не завершить R8 до появления внешнего тега.
- В рамках текущего поручения не выполняются commit, push, создание тега,
  GitHub Release или публикация AUR. Появление тега не считается разрешением
  изменять его. При необходимости изменить уже опубликованные исходники
  возвратить вопрос выпуска пользователю.

В T04 допускается проверить рецепт на временной копии с локальным архивом
текущих подготовленных исходников. Подмена источника не переносится в финальный
рецепт и не закрывает R8. Финальные SHA-256 и `.SRCINFO` заполняет T05 по
реальному архиву тега: рецепт упаковки может быть завершён после публикации
исходного тега, самоссылочный checksum архива внутри этого же архива не требуется.
До этого комплект помечается предварительным, `SKIP` не является финальной
проверкой целостности.
