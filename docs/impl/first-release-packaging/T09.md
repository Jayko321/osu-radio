# T09. CI и согласованный релизный staging по одному SHA

Состояние: workflow и candidate staging реализованы и локально проверены;
реальный CI, лицензионная сверка и финализация не выполнены.
Источники: [спецификация](../../specs/first-release-packaging.md), R7, финализация R3;
[план](../first-release-packaging.md), версия/источник, этап 6 и раздел 7.
Зависимости: T07 — два рецепта, архив обновлённой T05 и их генерация;
T08 — Windows pipeline; внешний вход — окончательный commit и реально
перенесённый `v0.1.0-alpha` для финального комплекта.

## Результат

CI собирает выбранный SHA нативно на Windows и в Arch-среде, сохраняя полный
проверяемый комплект: Setup.exe, бинарный архив для Arch, два Arch-рецепта (`-git`, `-bin`)
с `.SRCINFO`, SHA-256, manifest, licenses/Qt source materials и инструкции.
Публикация GitHub Release/AUR автоматически не выполняется.

## Границы и контекст

- Добавить release workflow в [.github/workflows](../../../.github/workflows/linux-ci.yml)
  рядом с Linux CI, переиспользуя скрипты T05/T07/T08. Не дублировать внутри YAML
  самостоятельные реализации упаковки. Windows/Linux получают один полный
  commit ID, а `-git` остаётся отдельно документированным вариантом main.
  Нужна проверка кандидата по SHA до финального переноса тега.
- Закрепить checkout/tool actions и фактические build tools/источники по
  контрактам предшественников; Linux-сборка выполняется в чистой Arch-среде
  с системным Qt по обновлённой T05, независимо от ОС orchestration runner. Сохранять logs/артефакты без секретов,
  не включать публикационные права и автоматический перенос refs.
- Версии [Qt](../../../apps/osu-radio-qt/Cargo.toml) и
  [server](../../../apps/osu-radio-server/Cargo.toml) уже `0.1.0-alpha`;
  проверить About/version metadata по фактическому UI, не повышать их.
- Manifest связывает исходный commit, tag/archive, OS/архитектуры, tool/runtime/Qt
  версии/patches, features/параметры, hashes всех конечных артефактов и
  Rust-бинарников в архиве для Arch. SHA-256 формируются после создания окончательных файлов.
  Для рецептов/.SRCINFO использовать release staging вне исходного commit,
  исключая цикл «binary checksum → новый commit → новый binary».
- Аудит лицензий по фактическим поставкам, не объединённый старый Arch inventory:
  Qt, self-contained .NET, native Realm, MSVC/дополнительные DLL/.so, Rust/assets.
  Сохранить обязательные полные тексты, соответствующие Qt sources/patches
  и сведения о замене динамических библиотек; ничего не считать проверенным
  только по наличию README. Дополнить общую краткую инструкцию всех форматов
  и затронутые guides.

## Проверка и приёмка

1. Проверить workflow/staging на candidate SHA без публикации. Ожидаются все
   три варианта поставки, одинаковый source SHA Setup и архива для Arch,
   соответствие `-bin` точному архиву T05, полные notices и проверяемый manifest.
   Проверка несуществующего SHA/отсутствующего artifact завершается ошибкой,
   не выпускает неполный комплект как успешный. Новую нетривиальную логику
   генерации manifest/checksums покрыть одним focused self-check.
2. Для финализации получить окончательный чистый source commit, доступный
   сборщикам. Перед внешним переносом сохранить старый commit
   `bf941c29b2e69fa73aca6c1c6a7c1643f3a7f3f9`, старые archive/desktop checksums
   из прежнего рецепта и пояснение о замене при той же версии. Это не разрешение
   самостоятельно делать commit/push/tag move: отдельное поручение обязательно.
3. После фактического переноса сверить peeled tag commit, содержимое полученного
   source archive и source SHA сборки. Повторить автоматизированную сборку
   из финального источника; byte-for-byte воспроизводимость бинарников новым
   требованием не вводится. Рецепт `-git` проверить на настоящем полном main.
4. Сгенерировать в staging окончательные два рецепта, `.SRCINFO` через
   `makepkg --printsrcinfo` в Arch-среде и конечные SHA-256. Проверить получение
   и clean build финального source recipe, установку `-bin` из точного архива,
   отсутствие candidate/local-source путей и `SKIP` для release-файлов.
5. Сверить hashes, версии, документацию и состав с скачанными CI artifacts.
   Неподтверждённый remote tag/архив, недоступный CI runner или непрошедшая сборка
   оставляют финальный критерий незавершённым; локальный candidate не заменяет
   этот результат. Передать T10 точные artifact hashes и инструкции. Полную
   физическую OS/audio приёмку не выдавать за результат CI.

## Отчёт о выполнении

2026-10-29, Linux x86_64: подготовлена независимая часть T09. Скрипт
[stage-arch-recipes.py](../../../packaging/release/stage-arch-recipes.py) берёт
оба PKGBUILD из указанного полного существующего commit, сверяет записанные в
архиве source SHA и `working tree: clean`, вычисляет SHA-256 архива, подставляет
его в копию `-bin` и формирует обе `.SRCINFO` через `makepkg` в новом staging.
Проверка основана на записанном provenance, а не независимом доказательстве
состава архива или подлинности сборки. Исходный рецепт остаётся с нулевой суммой.
[Инструкция Arch](../../../packaging/arch/README.md) и
[development guide](../../agent/development.md) дополнены.

`python3 -B -m unittest discover -s packaging/release -p 'test_*.py' -v` прошёл:
из синтетического архива и временного Git-репозитория получены оба `.SRCINFO`
настоящим `makepkg`, проверены SHA, VCS `SKIP`, отсутствие `SKIP` для архива,
игнорирование незакоммиченного изменения рецепта и отказ при несуществующем или
несовпадающем SHA, отсутствующем файле, грязном provenance и повторном staging.
Реальный грязный архив T05 отдельно отклонён по `working tree: DIRTY`.
Ни синтетическая фикстура, ни грязный T05 не являются CI-кандидатом.

Сохранены прежние данные для объяснения замены при той же версии: локальный
`v0.1.0-alpha^{}` — `bf941c29b2e69fa73aca6c1c6a7c1643f3a7f3f9`;
архив исходников в прежнем рецепте SHA-256
`15fa8e08b960cf00a47ec1ae935bf90c774bfccc17dc82f1100b0bf3668f1566`,
`osu-radio.desktop` SHA-256
`f99337fc9f9d60437461a3e887b0f6259202de5774224f611b85eb6f03b1b2b9`.
Суммы прочитаны из `HEAD:packaging/arch/PKGBUILD`, desktop отдельно сверен с
файлом старого commit; архив и remote tag заново не скачивались. После переноса
тега архив при той же версии будет содержать новые исходники, а не старый commit.

Статически Qt и server имеют `0.1.0-alpha`; `main.rs` передаёт Cargo version в
Qt, а About показывает `Qt.application.version`. UI реально не запускался.
HEAD `c9f2500bad0c645d4e5e2db5dcdd9f6b712ac551` не содержит скриптов T05/T07/T08,
рабочее дерево содержит незакоммиченные изменения. Позднее T08 собрала отдельный
Windows candidate в GitHub Actions и частично проверила его в Wine (см. T08),
но проверенные финальные источники/pins и лицензионный inventory отсутствуют.
Поэтому общий release workflow, CI run по одному SHA,
выбор доступного сборщикам SHA, Setup/archive, общий manifest, license audit,
сверка Qt sources/patches и финальные hashes не выполнены. После завершения T08
нужно интегрировать скрипт в CI, проверить его на настоящем clean candidate,
затем выполнить все проверки 1–5. Коммит, push, перенос тега и публикация не
выполнялись; T10 остаётся зависимой от итогового комплекта и его hashes.

### Продолжение T09, 2026-10-29

Предыдущий отчёт сохранён как свидетельство раннего состояния. Указанное в нём
отсутствие общего workflow/manifest устранено на уровне исходников; отсутствие
чистого общего commit, проверенных Windows-материалов и финального тега сохраняется.
Текущий HEAD по-прежнему `c9f2500bad0c645d4e5e2db5dcdd9f6b712ac551`, рабочее дерево
содержит прежние изменения упаковки и несвязанные поиск/БД; они сохранены.

**Реализация.** Добавлены:

- [release-staging.yml](../../../.github/workflows/release-staging.yml): только
  ручной запуск с полным SHA, `contents: read`, одинаковый checkout всех jobs,
  Windows MSVC и Arch-контейнер, передача двух handoff artifacts, отдельный staging
  и logs. Все actions закреплены commit IDs; внутренний Qt action вызван напрямую,
  поскольку его composite wrapper содержит плавающие ссылки. `.SRCINFO` явно
  включаются в upload. Нет commit/push/tag/publish шагов.
- [ci-windows.ps1](../../../packaging/release/ci-windows.ps1) и
  [ci-arch.sh](../../../packaging/release/ci-arch.sh): оркестрация существующих
  T08/T05 builders. Windows проверяет Inno installer hash/signature; версия
  MSVC/SDK проверяется существующим builder. В
  [Windows build.py](../../../packaging/windows/build.py) добавлены явное
  clean/dirty состояние, OS/Python, фактический helper runtimeconfig и SHA-256
  полученного Setup для handoff.
  Arch использует `/work`, как проверенный T05 helper publish; прежняя точная
  сверка helper inventory сохранена и остановит сборку при изменении его файлов.
- [inputs.json](../../../packaging/release/inputs.json): pins из T08 и проверенные
  официальный Arch image digest
  `sha256:e82623936fa1a69700b48e98b058df6eaab18b737c27473a7234a40fdecb9413`,
  snapshot `2026/10/29`. Digest manifest сверён с полученными байтами Docker

  `0b720f1750ea22fd3d7b571a09f41832c9805f0f62838eb0e5f389967785236d`.
  Сам контейнер в этой работе не запускался. URL/hash проверенного комплекта

- [stage.py](../../../packaging/release/stage.py): проверка чистого checkout и
  версии `0.1.0-alpha`, безопасное получение materials по SHA-256, сверка

  соответствие Arch notices исходникам, повторное использование генератора
  рецептов T07. SHA Rust-бинарников вычисляются из содержимого Arch-архива.
  Manifest включает source SHA, параметры/tools, Qt sources/patches, CI identity

  Итоговый каталог появляется только после успешного завершения генерации.

  **не** выдаётся за скачанный архив перенесённого тега. Manifest остаётся
  candidate с `verified_remote_tag: null`.
