# План реализации поиска по библиотеке

Статус: техническое решение согласовано; карточки T01–T08 подготовлены.
T01–T08 реализованы и проверены в объёме своих карточек; пользовательская приёмка всей спецификации открыта.
Дата: 2026-11-06.

## 1. Источник, цель и существующий код

Источник требований — [спецификация поиска](../specs/library-search.md), R1–R12.
Цель — добавить расширенный поиск Songs, сохранив группировку по аудио, все
связанные сложности, сортировку и управление воспроизведением.

Оба HTTP endpoint сходятся в `BeatmapSetService::matching_audio_ids`. Сервис
пересекает найденные audio ID, а репозиторий выполняет поиск по нормализованным
полям. Полные результаты загружаются порциями по 500 audio ID внутри одного
снимка чтения. Эти механизмы сохраняются:
[сервис](../../crates/radio-services/src/beatmap_set.rs),
[репозиторий](../../crates/radio-db/src/repositories/beatmap_set.rs).

Клиент уже обеспечивает задержку 200 мс, отмену запросов и отбрасывание
устаревших ответов. BPM, online set ID и импортированные даты игры уже хранятся.
Stars, статусы, даты ranked/submitted и поисковую длительность нужно добавить.

Согласовано пользователем:

- Заполнение новых данных при импорте и Refresh; существующие неизвестные
  значения сохраняются до обновления папки.
- Основной отбор в SQL, узкая проверка границ фраз в Rust. Это сохраняет
  существующую обработку без загрузки поискового текста всей библиотеки в Rust.
- Общая подготовка длительности в `radio-services`, с переносом существующего
  Lofty probe; использование Tokio, chrono и regex. Новые crates проекта не нужны.
- Временная нормализация stable: код 2 → `pending`, код 1 → `none`.
- Допуск BPM применяется только к `=` и `!=`; остальные операторы сравнивают
  без допуска.

## 2. Данные, импорт и совместимость

Добавить следующую версионную миграцию после v18, не изменяя исторические
миграции.

| Владелец данных | Расширение |
| --- | --- |
| Сложность: ImportedBeatmap → beatmaps | Nullable сохранённые stars и нормализованный статус |
| Набор: ImportedBeatmapSet → beatmap_sets | Nullable даты ranked/submitted в Unix milliseconds UTC |
| audio_sources | Nullable полная длительность `duration_ms` |
| beatmap_metadata | Производные нормализованные поля имени mapper и source |

Нормализованные mapper/source заполнить из уже сохранённых метаданных
ограниченными страницами, по образцу миграции v17. Остальные новые поля старых
строк оставить неизвестными. Immutable metadata hash и исходное содержимое
метаданных не менять; библиотека, плейлисты, история и настройки сохраняются.
Контракты хранения и замены снимка — в [database guide](../agent/database.md).

### Импорт stable

В [reader](../../crates/radio-scanner/src/stable/reader.rs) перестать пропускать
статус, игровой режим и таблицы stars. Выбирать запись `mods=0` из таблицы
исходного режима; отсутствие таблицы или записи означает неизвестный рейтинг.
Сохранить чтение поддержанных форматов float/double и проверки структуры.

Коды 4–7 соответствуют ranked/approved/qualified/loved; 2 временно становится
pending; 0, 1, 3 и неизвестные коды — none. Даты ranked/submitted остаются
неизвестными.

Ограничение stable зафиксировано в спецификации; отразить его также в scanner
guide. Рядом с преобразованием добавить `shortcut:`: код 2 объединяет
pending/wip/graveyard; пересмотреть при изменении или удалении поддержки stable.
Само удаление stable сюда не входит. Ограничение подтверждено
[официальным форматом osu!.db](https://github.com/ppy/osu/wiki/Legacy-database-file-structure).

### Импорт lazer

Согласованно расширить
[NDJSON helper](../../tools/osu-lazer-realm-parser/Program.cs),
[Rust DTO](../../crates/radio-scanner/src/lazer/types.rs) и импортные типы:
`Beatmap.StarRating`, `Beatmap.Status`, `BeatmapSet.DateSubmitted`,
`BeatmapSet.DateRanked`. Отсутствующие поля и sentinel stars `-1` дают
неизвестное значение. Статус нормализуется по смыслу enum источника; числовые
коды lazer не совпадают с кодами stable.

Сохранённые stars относятся к исходному режиму без модов; самостоятельный
расчёт не добавляется. Источники закреплённой ревизии спецификации:
[BeatmapInfo](https://github.com/ppy/osu/blob/77df204df2e217cdbf884cf4ce9aaa442ce21e07/osu.Game/Beatmaps/BeatmapInfo.cs),
[BeatmapSetInfo](https://github.com/ppy/osu/blob/77df204df2e217cdbf884cf4ce9aaa442ce21e07/osu.Game/Beatmaps/BeatmapSetInfo.cs),
[BeatmapUpdater](https://github.com/ppy/osu/blob/77df204df2e217cdbf884cf4ce9aaa442ce21e07/osu.Game/Beatmaps/BeatmapUpdater.cs),
[DifficultyCalculator](https://github.com/ppy/osu/blob/77df204df2e217cdbf884cf4ce9aaa442ce21e07/osu.Game/Rulesets/Difficulty/DifficultyCalculator.cs).

### Длительность

Перенести существующий
[probe](../../apps/osu-radio-server/src/routes/media.rs) из server в
`radio-services`, сохранив определение формата по содержимому, отказ от открытия
специальных файлов и текущую обработку ошибок.

При импорте/Refresh после чтения источника, до начала записывающей транзакции,
определить длительность каждого уникального аудио один раз. Использовать
последовательные `spawn_blocking` операции без постоянного фонового worker.
Подготовленные значения записывать вместе со снимком; проводить эту подготовку
и для CLI. Точки интеграции — `OsuInstallationService`:
[регистрация и Refresh](../../crates/radio-services/src/folder_selection.rs),
[замена снимка](../../crates/radio-services/src/osu_installation.rs).

Недоступный, повреждённый или неподдерживаемый файл даёт неизвестную длительность
и не отменяет импорт. При Refresh записывается результат текущей подготовки,
включая неизвестное значение, без сохранения устаревшей длительности.

HTTP duration и playback продолжают проверять файл через общую функцию. Поиск
использует сохранённую длительность снимка; её актуализация происходит при
Refresh. Во время поиска аудиофайлы не открываются.

## 3. Разбор запроса и выполнение поиска

- Разбор разместить в модуле поиска `radio-services`. Типизированные критерии
  запросов репозитория принадлежат `radio-db`; SQL остаётся в репозиториях.
  Новые HTTP endpoints не нужны.
- Парсер сохраняет последовательность условий и исходные фрагменты.
  Неизвестное поле, неподдерживаемый оператор, пустое/невалидное значение и
  незакрытые кавычки остаются обычным текстом. Повторные условия не
  перезаписываются.
- Поддержать алиасы спецификации. Для операторов `:` соответствует `=`, `!:` —
  `!=`, `<:` — `<=`, `>:` — `>=`. Пользовательский текст передаётся SQL
  параметрами и не становится регулярным выражением.
- Подстроки и полное совпадение проверять по нормализованным полям в SQL. Для
  фраз сначала отбирать кандидатов по подстроке, затем потоково проверять только
  нужные поля в Rust. Не собирать текст всей библиотеки в памяти.
- Границы фраз воспроизвести по правилам `.NET \b`, включая начало/конец поля.
  Обычный Rust `regex::\b` имеет другой набор Unicode-категорий, поэтому нужен
  небольшой отдельный matcher границ. Нормализация остаётся существующей —
  Rust `to_lowercase()`. Источники:
  [правила Rust regex](https://github.com/rust-lang/regex/blob/master/UNICODE.md),
  [.NET boundary implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Text.RegularExpressions/src/System/Text/RegularExpressions/RegexCharClass.cs).
- Положительные условия пересекать на уровне audio ID. Отрицательные
  текстовые/status условия исключают аудио при любом совпадении среди связанных
  записей. Фраза проверяется внутри одного поля или отдельного тега.
- Все сравнения одного числового поля, включая `!=`, должны выполняться на
  одном известном значении. Разные поля могут совпадать в разных связанных
  сложностях. Stars перед сравнением усекаются вниз до сотых. Для BPM `=180`
  включает диапазон `[179,5; 180,5]`, `!=` — его дополнение среди известных
  значений.
- Календарные даты разбирать через chrono в интервалы UTC
  `[начало, следующий период)`. Равенство означает принадлежность периоду;
  `>` начинается со следующего периода. Неизвестная дата не проходит ни одно
  сравнение, включая `!=`. Повторные условия одного поля проверяются на одной
  дате.
- `played` и `lastplayed` используют максимум импортированной даты игры по
  аудио. Текущее время фиксируется один раз на запрос; история osu!radio не
  участвует.
- Если после выделения условий свободный запрос является одним положительным
  целым числом, объединить текстовые совпадения с совпадениями online set ID,
  затем применить остальные условия.
- После отбора сохранить существующую загрузку полных связанных данных
  порциями по 500 ID, порядок и единый снимок чтения. Для пустого запроса
  сохранить также legacy-поведение `/api/beatmap-sets` с пустыми наборами.

Форма HTTP-ответов не меняется. Qt и клиент продолжают передавать исходный `q`;
поиск плейлистов и настроек остаётся вне задачи. Описание `q` в HTTP/OpenAPI
должно отражать расширенный синтаксис.

## 4. Крупные этапы

1. **Данные и миграция:** импортные типы, модели, репозитории, nullable-поля,
   нормализованные mapper/source и проверка сохранности старой базы.
2. **Подготовка снимка:** stable/lazer mapping, реальные Realm-фикстуры, общий
   duration probe, включение подготовки в серверный и CLI импорт. Зависит от
   моделей и записи новых данных первого этапа.
3. **Поисковый механизм:** парсер, SQL-критерии, проверка фраз, общая интеграция
   двух endpoint. Парсер можно разрабатывать независимо; проверки данных
   требуют первого этапа, сквозной импорт — второго.
4. **Приёмка и документация:** сквозной Songs-сценарий, необходимые проверки и
   обновление затронутых guides, описания `q` и свидетельств R1–R12. Зависит от
   готовности предыдущих этапов.

Существующие изменения пользователя в документации сохранять. Исходную
спецификацию не переносить и не переименовывать. Декомпозиция этих крупных
этапов приведена в разделе 7.

## 5. Проверка результата

Основные риски — неверные отрицания и диапазоны при общем аудио, потеря данных
при миграции/Refresh, ошибки импортного формата и расхождение SQLite/PostgreSQL.

| Проверка | Содержание |
| --- | --- |
| Парсер и matcher, R2–R11 | Алиасы, кавычки, буквальный fallback, Unicode-границы, форматы времени, границы BPM и календарных периодов |
| Сервисные контракты на обоих backend, R1–R11 | Разные сложности/наборы одного аудио, отрицания, диапазоны на одном значении, неизвестные данные, MAX lastplayed, сохранение всех сложностей |
| Импорт, R6–R9 и R11 | Stable layouts и float/double stars; исходный mode/no-mod; реальные временные Realm-фикстуры, новые поля и их отсутствие |
| Длительность, R6 и R11 | Переиспользовать MP3/Ogg/WAV и FIFO-тесты probe; добавить проверку сохранения полной длительности при импорте/Refresh |
| Миграция и снимок, R12 | Обновление заполненной v18, нормализация mapper/source, сохранность плейлистов/истории, rollback и атомарность обновления новых данных |
| HTTP и Songs, R12 | Один запрос с полем/кавычками через оба endpoint; существующие encoding/debounce/cancellation тесты; ввод, результат и очистка с прежней сортировкой на реальном backend |

Матрицу поиска держать на сервисном уровне; HTTP и GUI проверяют свои
взаимодействия. Расширять существующие fixtures и smoke-сценарии, не создавать
отдельную тестовую инфраструктуру. Основные точки переиспользования:

- [Сервисные search contracts](../../crates/radio-services/src/tests/search.rs),
  включая общую аудиогруппировку, порядок между порциями и снимок чтения.
- [Stable tests](../../crates/radio-scanner/src/stable/tests.rs),
  [lazer tests](../../crates/radio-scanner/src/lazer/tests.rs) и
  [Realm fixture generator](../../tools/osu-lazer-realm-parser/fixture-generator/Program.cs).
- `compact_http_preserves_legacy_tracks_and_every_difficulty` в
  [tracks route](../../apps/osu-radio-server/src/routes/tracks.rs).
- `search_debounces_cancels_and_ignores_late_success_and_error` в
  [client controller](../../crates/osu-radio-client/src/controller.rs).
- `songs_search_debounces_retries_and_clears_through_the_live_adapter` в
  [Qt launch smoke](../../apps/osu-radio-qt/tests/launch_smoke.rs). Его fixture
  server не заменяет сквозной сценарий с настоящим backend.

Запустить затронутые core/scanner/helper, DB/services и CLI проверки, server
с `docs` и без него, выбранные client/Qt проверки, formatting и scoped Clippy.
Команды и разделение backend — в
[verification matrix](../agent/development.md#verification-matrix).
PostgreSQL проверять только в одноразовой `radio_db_test_*`; socket-тесты — на
разрешённом runner. `--all-features` не использовать. Источники для проверки
импорта задавать явно, без обхода пользовательских дисков.

В окружении найдены Cargo, .NET, Qt `qmake6` и `psql`; работоспособность сборок и
доступность тестового PostgreSQL при планировании не проверялись. Числовые
требования производительности не вводятся. Offscreen-проверки не подтверждают
нативное поведение Windows; физическое воспроизведение не проверяется этой
матрицей.

## 6. Готовность к выполнению и следующий шаг

Существенные решения согласованы. При подготовке карточек план сверен с текущими
исходниками, вызывающими участками, миграциями и существующими проверками;
расхождений, требующих пересмотра решения, не обнаружено. Входные документы:

- `docs/specs/library-search.md`;
- `docs/impl/library-search.md`.

Следующий шаг выбирает пользователь: [$impl-exec](/home/jayko/.codex/skills/impl-exec/SKILL.md)
для одной карточки. Пример поручения:
«$impl-exec, выполни карточку docs/impl/library-search/T02.md; запиши результаты проверок».
Указание следующего скилла не запускает реализацию. Перед выполнением сверить
актуальность входов и завершение зависимостей; при существенном расхождении
уточнить план через `$impl-plan`, сохранив остальные договорённости.

При подготовке плана исследованы исходники проекта и указанные upstream
источники; продуктовый код не изменялся, тесты, импорт и приложения не
запускались. Остаются согласованные ограничения: новые данные старой библиотеки
требуют Refresh, статусы stable частично объединены, импорт потребует
дополнительного чтения аудиофайлов. Фактические результаты проверок относятся
к последующему выполнению задачи.

результат предшественников. Каждая карточка включает свою проверку и обновление

### Общие условия выполнения

- Сохранять существующие пользовательские правки guides. На момент
  декомпозиции они есть в `backend.md`, `database.md`, `frontend.md`, `index.md`
  и `scanner.md`; план и спецификация ещё не отслеживаются Git. Это не поручение
  на commit, публикацию или изменение этих сторонних правок.
- Карточки описывают планируемые проверки. При декомпозиции выполнена только
  статическая сверка исходников и документов; тесты, импорт, БД и GUI не запускались.
- `tests/search.rs::contracts` вызывается из `sqlite_service_contracts` и
  `postgres_service_contracts`; один фильтр `cargo test ... search` не выполняет
  эту матрицу. PostgreSQL запускать отдельно, с одноразовой `radio_db_test_*` и
  `RADIO_DB_TEST_POSTGRES_URL` по [development guide](../agent/development.md#repository-and-backend-checks).
- Использовать [verification matrix](../agent/development.md#verification-matrix),
  не объединять несовместимые backend features. Проверки с сокетами выполнять
  на разрешённом runner; источники импорта и БД задавать явно.
- Выполненные проверки фиксировать в карточке. Переиспользовать результаты,
  пока код, зависимости и окружение не менялись; после изменения повторять
  затронутые проверки. Не повторять всю матрицу только ради итогового отчёта.
- Готовность карточек означает определённые входы и приёмку. Она не означает
  готовность реализации или пользовательскую приёмку. T08 переносит существенные
  результаты и ограничения в спецификацию; удаление рабочих документов сейчас
  не выполняется.
