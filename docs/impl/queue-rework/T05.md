# T05. Серверный обработчик проверок доступности

Состояние: реализовано; обе серверные SQLite-конфигурации проверены. Пользовательская приёмка отдельно.
Источники: [спецификация](../../specs/queue-rework.md), R2, R3, R5, R7, R10;
[план](../queue-rework.md#34-фоновая-проверка-доступности), §3.3–3.5, §5.
Зависимости: T04 — атомарное обновление источников и сохранённые `checking`;
через неё T02 — guarded-результаты и переходы с намерением playing/paused.

## Результат

Один управляемый обработчик сервера проверяет файлы вне транзакций записи,
не более четырёх одновременно. Незавершённые проверки восстанавливаются из БД,
результаты безопасно применяются и публикуются после commit.

## Границы и контекст

Контракт T04: `pending_checks()` выбирает актуальные источники из записей очереди,
а не из `QueueState.launch_source`. Назначенный запуск может сохранять старый audio-ID
и token при новом checking-источнике записи. Проверить старый результат после удаления,
восстановления и смены файла; результат новой проверки не меняет назначенный запуск.
Успех ожидающей записи фиксирует launch-source без смены token; потеря её источника
в библиотечной транзакции уже переводит дальше с сохранением playing/paused.
Повторить интеграцию подбора после импорта и lost post-commit notification.

Использовать `QueueService::pending_checks()` / `apply_check(QueueCheck, bool)` из T02. Приоритет определяется сохранённым `waiting_for_check`; `checking` текущей записи само по себе не означает ожидание. Успех ожидающей сохраняет token/режим, результат уже назначенной записи не прерывает запуск.

- Опорные точки: [AppState](../../../apps/osu-radio-server/src/state.rs),
  [serve](../../../apps/osu-radio-server/src/main.rs),
  [выдача аудио](../../../apps/osu-radio-server/src/routes/media.rs),
  [committed_response и events](../../../apps/osu-radio-server/src/routes/playback.rs),
  сервисные контракты T02/T04. Сверить их фактические имена по отчётам.
  Работник принадлежит lifecycle сервера, не создаёт отдельного владельца очереди.
- Проверять обычный файл и возможность открыть на чтение без декодирования;
  переиспользовать правила audio route, включая отказ для FIFO до открытия.
  Путь разрешает сервер, клиент и Qt не получают доступ к исходным файлам.
- Подбирать задания из сохранённых состояний; отдельной таблицы заданий нет.
  Текущая ожидающая запись приоритетна. Подхватывать `checking` после старта
  и повторно подбирать после потерянного post-commit уведомления, не перепроверяя
  already available/unavailable при старте или открытии панели.
- Применять результат короткой транзакцией только при совпадении entry-ID,
  поколения и привязки источника. Исключить дубли одновременно запущенных задач,
  зависшие `checking` после ошибок задач и запись результата после завершения
  обработчика. Завершение/отмена работника должны быть проверяемы и не оставлять
  живые задачи/владение AppState через цикл ссылок.
- Успех проверки текущего ожидающего запуска разрешает воспроизведение;
  недоступность переводит к следующей записи с сохранением playing/paused.
  Добавленные без Play и полностью недоступные плейлисты без нового Play
  не запускаются. Настоящий Started присылает клиентский движок, дата от проверки
  не меняется. Уже звучащее локальное аудио не останавливается от одной доступности.
- Публиковать committed revision через существующий монотонный watch/NDJSON
  путь; ошибки/rollback и stale результаты не публикуют выдуманное изменение.
  Подключить имеющиеся точки добавления/импорта и future hooks для T06;
  потеря уведомления компенсируется повторным подбором.
- Обновить [backend](../../agent/backend.md) и факты lifecycle в
  [architecture](../../agent/architecture.md), не меняя утверждённые границы.

## Проверка и приёмка

Добавить детерминированные серверные тесты с временными файлами и управляемым
завершением задач: обычный читаемый файл, отсутствующий файл, каталог, FIFO
на Unix; ни один тест не должен зависать на open. Через барьеры/управляемую
проверку доказать максимум четыре одновременных операции и приоритет текущей.
Проверить restart с `checking`, потерю уведомления, ошибку задачи, остановку
работника и callback после неё, удаление/очистку/reimport во время проверки.
Старые ID/поколения/привязки не меняются. Проверенные записи при restart не открываются.

Проверить переход checking → available/unavailable с playing и paused намерением,
монотонные revision-уведомления после commit и отсутствие Started/даты без движка.
Append без Play не запускается при успехе проверки. Использовать и изолированные
тесты работника, и реальный AppState с временной SQLite-БД.

`cargo test -p osu-radio-server --locked`;
`cargo test -p osu-radio-server --no-default-features --features sqlite --locked`;
`cargo test -p radio-services --locked` при изменении сервисных контрактов.
Новые worker-тесты должны реально выполняться в обоих router feature-состояниях.
Новые HTTP-операции и их wire-контракт принимаются в T06; физический звук — T10.

## Отчёт о выполнении

Выполнено 2026-10-16 поверх фактических T01–T04, с сохранением незакоммиченных
изменений. Сервисные контракты, миграции, клиент и Qt в T05 не изменялись.

### Реализация и передача T06

- [QueueCheckWorker](../../../apps/osu-radio-server/src/queue_check.rs) запускается
  в `serve` после успешных state/listener/local_addr. Handle принадлежит `serve`;
  [AppState](../../../apps/osu-radio-server/src/state.rs) хранит только `Arc<Notify>`.
  Тестовые состояния сами worker не запускают.
- Startup, wakeup, завершение операции и секундный tick читают сохранённые проверки.
  Перед заполнением слотов заново вызывается `pending_checks()`. Одновременно не более
  четырёх `JoinSet::spawn_blocking`; active-ID сопоставлен полному `QueueCheck`,
  включая поколение и источник. Ошибка задачи, в том числе panic, освобождает слот;
  неудачные task/apply откладываются до следующего tick и диагностируются в stderr.
- [open_audio_file](../../../apps/osu-radio-server/src/audio_file.rs) объединяет
  прежние правила audio route: regular metadata до read-open и проверка дескриптора
  после него. Worker Local/Copied не декодирует данные и не держит write transaction.
  [Media route](../../../apps/osu-radio-server/src/routes/media.rs) сохраняет HTTP
  mapping ошибок, длину и ограниченные streaming chunks.
- Только supervisor последовательно вызывает `apply_check`; существующие guards
  T02/T04 проверяют ID, поколение и привязку. Успешный результат публикует committed
  revision через монотонный watch. Каждый scan также публикует сохранённый revision:
  библиотечное изменение без новых checks и потерянное post-commit уведомление
  подхватываются при следующем секундном подборе при доступной БД.
- [committed_response](../../../apps/osu-radio-server/src/routes/playback.rs) будит
  worker после commit очереди/Play плейлиста до duration probing.
  [Import/reimport](../../../apps/osu-radio-server/src/routes/folder_selection.rs)
  и [удаление папки](../../../apps/osu-radio-server/src/routes/user_data.rs) подключены
  после успешного commit. **T06 использует `AppState::wake_queue_checks()` после commit**
  и сразу `publish_playback(revision)`, если revision уже получен; общий response helper
  делает оба действия. Новый HTTP DTO или сервисный API в T05 не добавлен.
- `shutdown` сигнализирует stop и ожидает supervisor. После stop новый подбор и
  новые apply не начинаются; уже начатая транзакция завершается до acknowledgement.
  Начатые файловые операции дожидаются, поздние результаты отбрасываются. После
  подтверждённого shutdown нет живых worker-задач или последующих записей. Drop
  инициирует ту же остановку; AppState не владеет handle, цикла владения нет.
  Прежний протокол принудительного завершения дочернего процесса не изменён.

### Проверки поведения

[12 worker-тестов](../../../apps/osu-radio-server/src/queue_check/tests.rs) выполняют
настоящий supervisor, Services и временную memory/file SQLite. Файловые операции
для scheduler/race tests управляются каналами start/release с ограниченным ожиданием;
отдельный тест использует реальные файлы. Это не проверка физического аудиодвижка.

| Область | Фактическое свидетельство |
| --- | --- |
| Файлы | Local и Copied читаемого файла с неаудиобайтами доступны; отсутствующий файл/каталог недоступны. Unix FIFO отклоняется до open; при регрессии тест освобождает блокирующий open перед join. Общий helper также проходит существующие HTTP streaming/error tests. |
| Планировщик | Четыре удерживаемые операции исключают пятую; повторные wakeup не дублируют задания. Play другой ожидающей записи при занятых слотах отдаёт следующий освободившийся слот ей. |
| Recovery/retry | Повторный AppState на файловой БД открывает только checking, пропуская checked available/unavailable. Пропущенный wakeup компенсирует tick. Panic освобождает слот без ложного revision, тот же check выполняется на следующем tick. |
| Shutdown | При двух удерживаемых операциях shutdown не завершается до обеих; их результаты не меняют БД. После acknowledgement закрывается канал владельцев файловых closure. Drop также останавливает supervisor; late results не применяются. |
| Гонки | Remove/clear не принимают старый ID и не публикуют no-op. Reimport во время проверки меняет поколение/источник; старый результат не меняет новый доступный источник. Новая проверка уже назначенного запуска сохраняет его прежний launch-source/token. Удалённая папка не восстанавливается поздним success. |
| Переходы | Waiting success сохраняет token и Playing/Paused; failure переходит к следующей с прежним намерением. Append и восстановление полностью недоступного плейлиста остаются Stopped. Проверки не генерируют Started/дату. |
| Уведомления | HTTP append → проверка → удаление источника дают строго возрастающие committed revision в существующем NDJSON. Invalid HTTP append и пустой append не меняют очередь/watch. Потерянный library notification восстанавливается при отсутствии новых checks. Подписчики освобождаются после закрытия stream/watch. |

### Документы и границы

Обновлены backend, архитектурные факты lifecycle, coverage inventory, общий план,
hook в T06 и частичные свидетельства R2/R3/R5/R7/R10 в спецификации. Приёмка
полной спецификации остаётся T10; новый wire contract и client waiting — T06/T07.

PostgreSQL здесь проверен компиляцией/линковкой, не выполнением worker на сервере БД.
Сервисные тесты не повторялись: их исходники/контракты не менялись. Принудительный
сбой БД не инъецировался; retry/logging ветка apply-error проверена по исходнику,
а rollback/no-op сохраняют прежние сервисные гарантии. Windows, реальные osu!
установки/Realm, GUI и физический звук не проверялись. Shutdown может ожидать
начатый файловый I/O неограниченно: Tokio не гарантирует его принудительное прерывание.
