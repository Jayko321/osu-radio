# T06. REST-контракт очереди, NDJSON и ApiClient

Состояние: реализовано; обязательная транспортная матрица проверена. Пользовательская приёмка отдельно.
Источники: [спецификация](../../specs/queue-rework.md), транспорт для R1–R11;
[план](../queue-rework.md#35-http-контракты), §3.3–3.6, §5.
Зависимости: T05 — рабочие переходы, плейлистовые/импортные операции,
post-commit уведомления и lifecycle обработчика из T01–T05.

## Результат

Сервер и ApiClient используют один новый контракт полного списка и отдельных
операций по entry-ID. Playback response/stream передают текущий ID и доступность;
оба роутера, OpenAPI и HTTP-фикстуры совпадают с контрактом.

## Границы и контекст

Контракт T05: `serve` владеет `QueueCheckWorker` и ожидает `shutdown`; состояния
тестов запускают worker явно. Все новые операции после commit вызывают
`AppState::wake_queue_checks()`, а при наличии committed revision сразу вызывают
`publish_playback(revision)` до последующих await. `committed_response()` уже делает
оба действия. Импорт/reimport/удаление папки подключены; секундный подбор восстанавливает
потерянные уведомления, в том числе при отсутствии новых checks. Новые DTO в T05
не добавлялись. Lifecycle и 12 тестов приведены в [отчёте T05](T05.md#отчёт-о-выполнении).

Контракт T04: assignment назначенного запуска возвращает сохранённый audio-ID,
даты и громкость старого источника; полная запись очереди содержит актуальные ссылки
и может быть checking/unavailable при прежнем token и `waiting_for_check=false`.
Не пересобирать assignment из актуальной строки очереди. Launch-source хранится на
сервере и не требует нового публичного объекта DTO. Повторить REST/NDJSON и обе
документационные конфигурации для reimport, поздних Started/Failed и проверки нового
источника; уведомление отправляется только после общей библиотечной транзакции.

Передать сохранённый `waiting_for_check` из QueueSnapshot/PlaybackAssignment в wire DTO. Не выводить ожидание только из availability: текущая checking может относиться к уже назначенному запуску без ожидания.

### Окончательный контракт для T07

`QueueState = {entries, current_entry_id, history_len, mode, waiting_for_check,
revision, playback_token}`. Старых массивов, индекса и `upcoming_tracks` нет.

`QueueEntry = {id, position, audio_source_id, playlist_item_id, title,
title_unicode, artist, artist_unicode, difficulty_name, beatmap_id,
beatmap_set_id, cover_beatmap_id, availability, last_played_at_ms, volume_percent}`.
Ссылки, подписи, дата и громкость nullable; ID, позиция и availability обязательны.
Availability: `checking | available | unavailable`. Внутренние пути/ключи,
поколения, launch-source и migration evidence не передаются.

Клиентский `models::QueueEntryId` — отдельный positive i64 с `new`, `get`, Display
и строковой serde; максимум `"9223372036854775807"`. Серверный EntryId проверяет
тот же диапазон. JSON Number, отрицательные/нулевые/переполненные/не-десятичные
значения отклоняются. Будущие Qt/QML callers должны сохранять строку без JS Number.

Playback REST/NDJSON дополнены nullable `current_entry_id`, nullable `availability`
и обязательным сохранённым `waiting_for_check`. Waiting не выводится из checking.
При reimport прежний assignment сохраняет audio-ID, дату и volume старого источника,
а entries показывают новую привязку. Длительность probing допускается только при
available без ожидания; при checking — null, даже для существующего tone.mp3.

| ApiClient | Запрос |
| --- | --- |
| `queue()` | GET `/api/queue`, полный список |
| `insert_queue(&[QueueItemRef], QueuePlacement)` | POST `/api/queue/items`, обязательные `items` и `placement:end/next`; `Audio {audio_source_id}` / `PlaylistItem {playlist_id,item_id}` сериализуются с `type:audio/playlist_item` |
| `append_queue(&[i32])` | Та же typed вставка audio в конец |
| `append_playlist_to_queue(i32)` | POST `/api/playlists/{id}/queue`, без тела |
| `play_queue_entry(QueueEntryId)` | POST `/api/queue/items/{entry_id}/play`, без тела |
| `move_queue_entry(QueueEntryId, Option<QueueEntryId>)` | PATCH `/api/queue/items/{entry_id}`, обязательное `before_entry_id`; null — конец |
| `remove_queue_entry(QueueEntryId)` | DELETE `/api/queue/items/{entry_id}` |
| `clear_upcoming_queue()` | DELETE `/api/queue/upcoming` |
| `clear_queue()` | DELETE `/api/queue`, весь список |

Все изменения возвращают PlaybackAssignment. Неизвестные entry/anchor/playlist,
missing/Online audio и неизвестный/чужой playlist item дают **404**. Play существующей
unavailable — **400**. Стандартный extractor сохраняет **400** для JSON syntax и
неверного path-ID, **422** для wrong type/variant/required body field; безопасный
**500** остаётся общим. Нет version fallback. `POST /api/playlists/{id}/play`
сохраняет R7; OpenAPI учитывает optional тело этого существующего маршрута.

### Свидетельства поведения

| Критерий | Проверка и результат |
| --- | --- |
| Полная очередь и GET без эффектов | Roundtrip ApiClient ↔ настоящий Axum/SQLite: past/current/future, повтор аудио с разными entry-ID, Unicode, difficulty, даты/volume, nullable references и unavailable. Состояние после повторного GET точно равно исходному, включая внутренний issued-ID counter. |
| Метод/путь/тело | HTTP-фикстуры проверяют каждый новый wrapper, оба placement, оба item variant, максимальные строковые path/anchor ID и явный null anchor. Реальный server roundtrip выполняет все методы. |
| Валидация/атомарность | Invalid second audio/Online/foreign item, unknown playlists/items/entries/anchors дают 404; missing/null/wrong/overflow тела и IDs отклоняются extractor. Очередь, revision/token, issued-ID и watch остаются прежними; следующий успешный insert выдаёт следующий непропущенный ID. |
| Изменения/R7 | Move текущей сохраняет ID/token; remove другой и текущей на паузе, checking следующей, обе очистки; typed playlist item и whole-playlist append; пустой append — no-op; partially/wholly unavailable и explicit unavailable start сохраняют правила R7. |
| Worker/stream/reimport | Реальный worker: waiting/checking → available в NDJSON, без ложного Started. Reimport через service transaction и общий committed-response boundary сохраняет прежний назначенный источник/дату/volume/token при новой checking-привязке; late Started/Failed и stale повтор не повреждают её. Snapshot-before-first-frame, reconnect, stale notification, heartbeat и subscriber drop проверены прежними route tests. |
| Commit/rollback | Invalid HTTP batch не публикует watch; committed responses и worker revisions доходят в stream. Повторно выполнены сервисные T02–T04 проверки атомарности, общей транзакции и видимости commit/rollback. Lifecycle worker не менялся. |
| Максимальный ID | Настоящие HTTP requests принимают max path/anchor как валидный ID (404 при отсутствии), отклоняют overflow. Queue/PlaybackResponse/NDJSON encoder → независимые клиентские DTO сохраняют max точно в отдельном projection test; max не вставлялся raw SQL в HTTP fixture. |
| OpenAPI | Оба runtime-роутера содержат все методы/пути; docs suite сверяет полный набор маршрутов, resolvable refs, строковый EntryId, variants/placement и required/nullable свойства QueueResponse, QueueEntryResponse, PlaybackResponse, MoveRequest. |

### Границы

T07 получает окончательные DTO/методы/статусы выше. Клиент пока не ждёт проверки,
старый playlist Append ещё проецирует доступные audio-ID; подключение нового
whole-playlist метода, полноценная Queue VM и панель — T07–T09. Готовность R1 и
приёмка общего сценария R1–R11 этим не заявляются.

Проверки reimport используют синтетические snapshots и общий post-commit boundary,
без настоящего Realm reader. Ошибка БД посередине HTTP commit не инъецировалась;
rollback видимость проверена сервисными контрактами, отказ batch — HTTP-тестами.
PostgreSQL runtime не запускался, проверяется сборка/линковка. Реальные osu!
установки, нативная Linux/Windows GUI-приёмка и физический звук не проверены.
