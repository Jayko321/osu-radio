# Регулируемые скорость и pitch: план реализации

Статус: существенные решения согласованы; подготовлены карточки T01–T12.
Карточки T01–T11 реализованы; состояние и свидетельства указаны в таблице ниже.
Автоматическая интеграция на Linux проверена в T11; нативная пользовательская
приёмка (T12) и Windows не выполнены.

## Источник и цель

Источник — [спецификация R1–R8](../specs/adjustable-pitch-speed.md).
Реализовать DT/HT/NC с общей и индивидуальной настройкой, сохранением,
изменением во время воспроизведения и управлением через Qt.

Согласованные решения:

- Rodio сохраняется; для сохранения высоты используется Signalsmith Stretch.
  Это сохраняет существующие декодирование и вывод; новая зависимость имеет
  MIT-лицензию.
- Добавляется отдельный сервис модов и собственные HTTP-настройки — явный
  выбор пользователя вместо расширения сервиса громкости. Клиентским
  состоянием владеет `SettingsViewModel`.
- NC отображает состояние DT + `Adjust pitch`; отдельный профиль NC
  не хранится. Это исключает дублирование одного состояния.
- D переключает DT → NC → без модов; E включает/снимает HT.
  DT → NC сохраняет скорость.
- Плеер показывает время с учётом скорости: 4:00 при 1,5× становится 2:40.
- Индивидуальные профили передаются в DTO треков и назначений:
  перед Play не требуется дополнительный запрос профиля.
- В работу входят согласование MPRIS/SMTC и Discord, чтобы новая скорость
  не оставляла неверные показания во внешних интеграциях.

Эти решения дополняют спецификацию в части технической реализации,
цикла клавиш, отображения NC и шкалы времени. Требования R1–R8 остаются
источником остальных правил.

## Техническое решение

### Профиль, хранение и HTTP

- Профиль содержит `mode: none|dt|ht`, целочисленный `speed_percent`
  и `adjust_pitch`. Значение 120 означает 1,20×. Для `none`
  используется 100 и выключенный pitch. Диапазоны и шаг — по R1;
  DT с включённым pitch отображается как NC.
- Добавить `AudioModsService` через `Services::audio_mods()`.
  Общие настройки разместить в `user_data`, индивидуальные — в новой
  таблице `audio_mods` с ключом `(audio_kind, source_location)`,
  без внешнего ключа на библиотеку.
- Добавить следующую версионную миграцию. Начальное состояние — общий режим
  без модов. Сохранить существующие данные; включить новую таблицу
  в явный reset.
- Записи выполнять под существующей блокировкой singleton и одной
  транзакцией. Проверять диапазоны и сочетания параметров в сервисе
  и ограничениях БД.
- Предусмотреть `GET/PATCH /api/user-data/audio-mods` для режима
  и общего профиля; `PUT/DELETE /api/audio-sources/{id}/mods`
  для индивидуального профиля. PATCH сохраняет пропущенные поля;
  ошибочный запрос ничего не изменяет. Неизвестный ID аудио возвращает 404.
- Добавить nullable `mods` в библиотеку, элементы плейлистов, очередь
  и playback assignment, включая REST и NDJSON. Собирать профиль
  в существующей согласованной транзакции чтения. Для текущего запуска
  использовать сохранённый источник запуска, а не новую привязку строки.
- Отсутствующий индивидуальный профиль означает отсутствие модов независимо
  от общего набора. Удаление библиотеки сохраняет профиль; повторный импорт
  той же идентичности возвращает его. Переключение режима сохраняет оба набора.
- Существующие контракты громкости остаются самостоятельными. Запись модов
  не создаёт новый запуск и не меняет queue token/revision.

### Клиент и сохранение

- Добавить состояние модов в `SettingsViewModel` и поддержать его
  в Qt-адаптере и mock-модуле. Сохранение модов получает собственную очередь
  с объединением изменений одного адресата, задержкой 200 мс, Retry
  и завершением записей перед остановкой backend.
- Локальное изменение применяется сразу; ответы сохранения подтверждают
  запись и не перезаписывают более новое значение.
- Использовать один допуск к воспроизведению после загрузки громкости
  и модов. До готовности удерживать последнее назначение; ошибка загрузки
  не разрешает запуск с предположительно правильными параметрами.
- Расширить существующий `Assign` параметрами движка. Применять громкость
  и моды до первого `play`; изменение параметров того же запуска
  сохраняет позицию, паузу и token.
- Индивидуальное редактирование B обновляет B. Параметры звучащего A
  пересчитываются из его профиля. Смена общего/индивидуального режима
  пересчитывает текущий запуск.

### Обработка звука

- Добавить `signalsmith-stretch = 0.1.3` только в `osu-radio-player`.
  Движок получает атомарный набор скорости и признака изменения pitch;
  названия DT/HT/NC остаются вне движка.
- Без модов сохранить обычный путь. С `Adjust pitch` использовать изменение
  скорости Rodio; без него — потоковый адаптер Signalsmith с сохранением
  частоты. Возможности и требования сборки проверены по
  [Rodio 0.22.2](https://docs.rs/rodio/0.22.2/rodio/struct.Player.html#method.set_speed)
  и [Rust-обёртке Signalsmith](https://github.com/colinmarc/signalsmith-stretch-rs).
- Использовать ограниченные блоки PCM внутри существующего источника,
  без обработки всего файла заранее и без нового рабочего потока.
  Переключать параметры на границе блока, сохраняя положение аудио.
- Учесть предварительную подачу данных, задержку процессора, дробное
  соотношение кадров и окончательный вывод хвоста. EOF отправляется один раз
  после завершения обработанного аудио.
- Сохранить обработку ошибок и освобождение источника при остановке callback.
  Снимок сообщает фактические параметры и позицию исходного аудио.
  После смены скорости нельзя вычислять позицию простым умножением всего
  прошедшего времени на новую скорость.

### Время, интерфейс и интеграции

- Внутри движка хранить координаты исходника. Для плеера вычислять
  `position / speed` и `duration / speed`; обратное преобразование
  применять к перемотке.
- При смене скорости пересчитывать шкалу, сохраняя место в аудио.
  Для выбранного B длительность вычисляется по профилю B.
  Жест перемотки отменять при смене запуска или скорости.
  Исходную длительность в метаданных не перезаписывать.
- Добавить рядом с громкостью кнопку модов и popup: выбор мода, скорость,
  `Adjust pitch`, снятие модов, состояние сохранения и Retry.
  В [SettingsPanel](../../apps/osu-radio-qt/qml/SettingsPanel.qml)
  добавить независимый переключатель индивидуальных модов
  с поддержкой поиска.
- F1 открывает popup; D/E работают только внутри него. Мышь и клавиши
  используют одни клиентские команды. Смена редактируемого трека закрывает
  popup и исключает поздние изменения прежнего адресата.
  Новые QML-компоненты зарегистрировать в существующих ресурсах.
  Галерея остаётся офлайн.
- [MPRIS/SMTC](../../crates/osu-radio-media-controls/src/lib.rs)
  получают исходные координаты и фактическую скорость; MPRIS публикует
  изменение `Rate` и диапазон 0,5–2. Новое управление модами из ОС
  не добавляется. Это сохраняет предусмотренную протоколом интерполяцию
  позиции:
  [MPRIS](https://specifications.freedesktop.org/mpris/latest/Player_Interface.html#Property:Rate),
  [SMTC PlaybackRate](https://learn.microsoft.com/en-us/uwp/api/windows.media.systemmediatransportcontrols.playbackrate?view=winrt-26100).
- [Discord](../../crates/osu-radio-client/src/discord.rs) получает время
  с учётом скорости; изменение скорости вызывает обновление presence,
  включая состояние паузы.
- Обновить требования сборки, CI, Arch-рецепты и notices для Signalsmith
  и включённых C++-библиотек. Обёртке необходимы C++ и libclang.

## Крупные этапы

1. Реализовать профиль и аудиообработку с проверкой сигнала и транспорта.
2. Добавить миграцию, репозиторий, сервис, HTTP и проекции DTO.
   Этот этап независим от аудиообработки после фиксации профиля.
3. Соединить клиентское состояние, сохранение и worker после этапов 1–2.
4. Подключить Qt, галерею и интеграции; завершить проверки, сборочные
   требования и затронутые агентские руководства.

Это порядок реализации и зависимостей, а не готовые карточки.
Согласованные архитектурные дополнения при реализации записать
в агентскую документацию; обновить затронутые факты в руководствах
по БД, backend, frontend и разработке.

## Проверка результата

Основные риски — ошибочное наследование общего профиля, потеря сохранённых
настроек, изменение звучащего A при редактировании B, неправильная частота,
сброс позиции, неверная шкала перемотки и преждевременное завершение трека.
Переиспользовать существующие fixtures и проверки, указанные в спецификации.

| Уровень и требования | Минимальные существенные проверки |
| --- | --- |
| БД и сервис — R1, R3, R4 | Миграция заполненной БД, reopen, reset, сохранность прежних данных, общая идентичность аудио, удаление/переимпорт, отсутствие наследования общего профиля. |
| HTTP и DTO — R1, R3, R5 | Диапазоны и ошибочные запросы без частичной записи; PATCH/DELETE; профили во всех проекциях и обоих вариантах router с документацией и без неё. |
| Движок — R2, R5, R6, R8 | Известные частоты и длительность при HT/DT, обоих вариантах pitch и NC 1,20×; границы скорости, смена параметров, пауза, seek, EOF и хвост. Переиспользовать MP3 CBR/VBR, Ogg и WAV fixtures. |
| Клиент и worker — R3–R6 | Выбранный B при звучащем A, переключение режима, устаревшие ответы, ошибка загрузки, Retry, shutdown, параметры до первого play и автоматический следующий трек. |
| Qt и интеграции — R6, R7 и согласованная шкала | F1/D/D/D/E/E, мышь, фокус, поиск Settings, офлайн-галерея; шкала 4:00 → 2:40 и обратная перемотка; скорость MPRIS/SMTC и время Discord. |

Матрицу правил проверять в клиентском состоянии; остальные уровни покрывают
свои риски хранения, сериализации, DSP и взаимодействия.

При реализации выполнить scoped-проверки из
[матрицы разработки](../agent/development.md#verification-matrix):

- SQLite/PostgreSQL раздельно; PostgreSQL — только на свежих disposable БД
  `radio_db_test_*`, не на пользовательской БД.
- Server docs on/off, client mock on/off, player/media-controls,
  последовательные Qt-пробы и generated-import QML lint.
- Scoped Clippy, `cargo fmt --check` и `git diff --check`.
  Cargo `--all-features` не использовать.
- Обновить затронутые DTO fixtures и проверки запросов: новый обязательный
  этап загрузки модов не должен оставлять тестовые backend-модели неполными.
- Проверить сборку с новой зависимостью на Linux и Windows.

Общий пользовательский сценарий: настроить общий DT, включить индивидуальный
режим и получить 1× для треков без профиля; задать A NC 1,20× и B HT,
проверить сохранение после перезапуска и переимпорта. При звучащем A выбрать
и изменить B, затем явно запустить B. Изменять скорость и pitch на лету,
поставить на паузу, перемотать и дождаться следующего трека очереди.
Повторить запуск из библиотеки, плейлиста и очереди.

Завершить реальной приёмкой на Linux и Windows: прослушивание,
изменения на лету, перемотка, переход очереди, нативные клавиши Qt
и внешние интеграции. Автоматические проверки не подтверждают
качество звучания и отсутствие слышимых сбоев.

## Готовность решения к декомпозиции

Существенные решения согласованы; план готов к декомпозиции.
Оставшихся вопросов, препятствующих подготовке карточек, нет.

Принятые значения по умолчанию и границы:

- Новая активация DT/HT использует скорость из спецификации;
  переход DT ↔ NC сохраняет скорость.
- Клиент и сервер обновляются вместе; отдельная синхронизация настроек
  между клиентами не добавляется.
- Кодеки, исходные файлы osu!, идентичность аудио, данные громкости,
  очереди, библиотеки, плейлистов и истории сохраняются.

Исходный этап `$impl-plan` завершён без карточек. На этапе `$impl-tasks`
от 2026-10-20 подготовлены карточки и зависимости ниже; техническое решение
сохранено. Следующий этап — выполнение выбранной карточки через `$impl-exec`.

### Максимально параллельный порядок

Начать можно **T01 + T02 + T03 + T04 одновременно**. Это четыре независимых
проверяемых результата: persisted model, DSP, native protocol и presentation
component. Popup T04 ещё не подключён к живому клиенту; native T03 сначала
получает нейтральный rate 1× от старого caller. Это явно промежуточные состояния,
а не заявление готовности всей функции.

Не ждать завершения всей волны, если нужный предшественник уже готов:

- T01 закончена → T05 → T06. Хранение/API/состояние — одна цепочка.
- T02 закончена → T10, независимо от длительности T05/T06 и остальных веток.
- T02 + T03 + T06 закончены → T07. Это барьер соединения движка,
  настроек и воспроизведения.
- T07 закончена → T08; если T04 тоже закончена, одновременно начинать T09.
  Оставшаяся T10 может продолжаться параллельно.
- Объединены T01–T10 → T11 → T12. Linux и Windows приёмку внутри T12
  можно проводить одновременно на разных машинах; один владелец собирает отчёт.

Схема зависимостей (стрелка означает обязательный готовый результат):

```text
T01 → T05 → T06 ──┐
T02 ──────────────┼→ T07 ────────→ T08 ───────┐
T03 ──────────────┘       └──────→ T09 ───────┤
T04 ────────────────────────────→ T09        ├→ T11 → T12
T02 ────────────→ T10 ───────────────────────┘
```

На старте нет отдельной карточки «договориться о DTO»: профиль, его семантика,
передача в DTO, единицы времени и границы владельцев уже согласованы в этом
плане. Конкретные имена новых Rust/QML символов выбирает владелец компонента,
фиксирует в отчёте; зависимый исполнитель читает его до работы.
Это позволяет начинать четыре ветки сразу без пустой синхронизационной задачи.

### Контракты между параллельными ветками

| Граница | Обязательный смысл | Где появляется конкретный API |
| --- | --- | --- |
| Хранение → HTTP → состояние | `mode: none|dt|ht`, integer `speed_percent`, bool `adjust_pitch`; none=100/false; DT 101–200, HT 50–99; NC=DT+pitch. Общий режим и профиль отдельны от индивидуальных. | T01 определяет model/service, T05 wire/ApiClient, T06 клиентские команды/state. |
| Проекции → effective profile | Nullable mods — сохранённый индивидуальный профиль, включая когда режим выключен. Нет индивидуального профиля = none; global не наследуется. Assignment следует сохранённому launch source. | T01/T05; T06 вычисляет effective selected/current profiles. |
| Состояние → worker → Player | Единый набор speed + adjust_pitch, volume отдельно; допуск только после двух settings loads. Новые параметры того же entry/token не создают новый запуск. | T02 фиксирует engine setter/Snapshot; T07 расширяет Assign и связывает с T06. |
| Player → UI | Source position/duration и actual speed; presentation делит на speed, UI seek умножает один раз; метаданные не меняются. | T02/T07; T09 проверяет bindings и отмену drag по launch/speed. |
| Player → native/Discord | Native получает исходные координаты + actual rate; Discord получает скорректированное время, обновляется при rate change даже на паузе. | T03 native contract; T07 отдаёт worker данные; T08 подключает. |
| Popup → клиент | Popup получает состояние и выдаёт intents; бизнес-правила D/E, defaults и сохранение принадлежат Settings VM. Late edit прежнего адресата отклоняется. | T04 сигналы/входы, T06 команды/адресат, T09 связывает. |
| DSP → сборка | Единственная новая DSP dependency в player; C++/libclang, exact lockfile и полный состав встроенных библиотек. | T02 владеет manifest/lock; T10 — prerequisites/CI/упаковка/notices. |

Владельцы не вводят общий новый crate, второй event loop, отдельный NC effect,
новый worker thread или независимый регулятор pitch. Межклиентская синхронизация
и управление модами из ОС остаются за границей согласованного объёма.
Если фактический API не позволяет выполнить согласованный контракт без изменения
архитектуры, остановить затронутые карточки и вернуть вопрос в `$impl-plan`.

T02–T09 в своих отчётах сохраняют нужные изменения frontend/architecture с

интеграцию как готовую возможность. Перед сдачей всей функции T11 переносит
эти факты; откладывать документацию за пределы T11 нельзя.

Для параллельной работы предпочтительны изолированные рабочие копии с
переносом только файлов своей карточки. В общей рабочей копии не откатывать
чужие изменения и не запускать проверки по наполовину отредактированным
зависимостям. Cargo.lock имеет одного владельца T02; не применять cargo fmt
ко всему workspace при параллельных правках. Форматировать только свою область.
Общие Cargo target/.NET output и особенно Qt builds/probes согласовать и
запускать последовательно либо разделить build outputs. Итоговый Qt lint
использует generated imports из соответствующей свежей сборки.

Запись результата/состояния — в свою карточку. Общую таблицу плана обновлять
при передаче/объединении одним редактором, чтобы параллельные отчёты не конфликтовали.
Архивы/пакеты, `.serena/project.yml`, `CLAUDE.md` и другие исходные dirty changes
не входят в эти задачи и сохраняются.
