# T01. Хранение режимов и ключа порядка (миграция v16)

Состояние: выполнено, проверено (SQLite и PostgreSQL); пользовательская приёмка не проводилась.
Источники: [спецификация](../../specs/shuffle-repeat.md), R1, R3, R6;
[решение: данные](../shuffle-repeat.md#данные-radio-db-миграция-v16).
Зависимости: нет.

## Результат

База хранит режимы очереди и ключ исходного порядка записей; существующие базы
обновляются до Off/Off без сброса и потери очереди; репозиторий читает и пишет
новые поля, а `validate()` отвергает несогласованное состояние.

## Границы и контекст

- Владение: `crates/radio-db` (миграции, сущности, модель, репозиторий, тесты).
  Сервис очереди, сервер и клиент не менять — это T02 и далее.
- Миграция `m20261024_000016_queue_modes` — образцы: v14
  ([queue_launch_source](../../../crates/radio-db/src/migrations/m20261016_000014_queue_launch_source.rs))
  и v15; регистрация в `migrations/mod.rs`. Колонки и CHECK — по плану:
  `playback_queue.shuffle`, `repeat_mode ('off'|'all'|'one')`, `repeat_launch`,
  `queue_entries.shuffle_order BIGINT NULL`. Работает на SQLite и PostgreSQL.
- Downgrade отказывает, если состояние непредставимо в v15 (shuffle включён или
  repeat не `off`), иначе удаляет колонки; сверить с guarded downgrade в v14/v15.
- Модель [queue.rs](../../../crates/radio-db/src/model/queue.rs): `RepeatMode
  { Off, All, One }`, `QueueState { shuffle, repeat, repeat_launch }`,
  `QueueEntry { shuffle_order: Option<i64> }`; `validate()`: при `shuffle` у всех
  записей есть ключ, без `shuffle` — ни у одной. Проверить всех, кто строит
  `QueueState`/`QueueEntry` (сервис, тесты), и дать им значения по умолчанию,
  не меняя поведения.
- [QueueRepository](../../../crates/radio-db/src/repositories/queue.rs) использует
  сырой SELECT полей `playback_queue` и полную перезапись `queue_entries`: добавить
  новые поля в оба пути; сущности — `entities/queue.rs`, `entities/queue_entry.rs`.
- Для T02/T03 опубликовать в отчёте точные имена типов и полей.

## Проверка и приёмка

Расширить [tests/queue.rs](../../../crates/radio-db/src/tests/queue.rs) и
`migration_lifecycle.rs` (число версий в `assert_schema`):

- upgrade с заполненной очередью (как `populated_upgrade`, включая пустую и
  с текущей записью): записи, текущая, revision и token прежние, режимы Off/Off,
  `repeat_launch` false, ключи NULL; повторное открытие не меняет состояние;
- round-trip: shuffle + repeat All/One + ключи сохраняются и читаются; reopen;
- `validate()`: ключ при выключенном shuffle и отсутствующий ключ при включённом —
  ошибка; запись с недопустимым `repeat_mode` отвергается БД;
- downgrade: при Off/Off проходит и очередь цела; при включённом режиме — отказ
  без потери данных.

`cargo test -p radio-db --locked`; PostgreSQL — по
[матрице](../../agent/development.md#repository-and-backend-checks) с одноразовой
базой `radio_db_test_*` (`--no-default-features --features postgres -- --include-ignored`);
Clippy обоих вариантов из той же матрицы. Если PostgreSQL недоступен, критерий
остаётся явно непроверенным.

## Отчёт о выполнении

**Изменённые файлы.** Новая миграция
`crates/radio-db/src/migrations/m20261024_000016_queue_modes.rs` (регистрация в
`migrations/mod.rs`); `entities/queue.rs`, `entities/queue_entry.rs`;
`model/queue.rs`, `model/mod.rs`; `repositories/queue.rs`; тесты `radio-db`
(`tests/queue.rs`, `tests/migration_lifecycle.rs`, `tests/audio_mods.rs`,
`tests/playlists.rs`, `tests.rs`); `crates/radio-services/src/queue.rs` — два
конструктора `QueueEntry` получили `shuffle_order: None` (поведение не менялось).

**Имена для T02/T03** (все в `radio_db::model`):

- `RepeatMode { Off (по умолчанию), All, One }`, `Copy`; в `model/mod.rs`
  экспортирован. В `radio-services` реэкспорта пока нет — решает T02.
- `QueueState.shuffle: bool`, `QueueState.repeat: RepeatMode`,
  `QueueState.repeat_launch: bool` (по умолчанию `false`/`Off`/`false`).
- `QueueEntry.shuffle_order: Option<i64>`.
- `QueueState::validate()`: `entry.shuffle_order.is_some() == state.shuffle` для
  каждой записи; `save()` вызывает `validate()` до записи.
- БД: `playback_queue.shuffle`, `.repeat_mode` (`'off'|'all'|'one'`, CHECK),
  `.repeat_launch`; `queue_entries.shuffle_order BIGINT NULL`. `repeat_launch`
  не связан CHECK с `repeat_mode`: согласованность держит сервис (T03).

**Проверки (выполнены).**

- `cargo test -p radio-db --locked` — 10 passed.
- PostgreSQL: одноразовый локальный кластер, база `radio_db_test_repositories`;
  `RADIO_DB_TEST_POSTGRES_URL=… cargo test -p radio-db --no-default-features
  --features postgres --locked -- --include-ignored` — 6 passed (включая
  `postgres_repository_contracts` и жизненный цикл миграций). Повторный запуск на
  той же базе падает на `unrelated_table` — тесту нужна свежая база, не регрессия.
- `cargo test -p radio-services --locked` — 18 passed, 2 ignored (SQLite).
- `cargo clippy -p radio-db -p radio-services -p osu-radio-cli -p osu-radio-server
  --all-targets --locked -- -D warnings` и тот же набор с `--no-default-features
  --features postgres` — чисто. Рабочая область: `cargo check --workspace --tests`
  — сборка проходит после правки `radio-services`.

**Что покрыто тестами.** Upgrade с v11 с заполненной и пустой очередью (в т. ч.
текущая запись, остановленный режим): записи, current, revision, token прежние,
Off/Off, `repeat_launch` false, ключи NULL, reopen без изменений
(`populated_upgrade`). Round-trip shuffle + `One` + `repeat_launch` + ключи и
`All` без ключей, чтение второй сессией. `validate()` отвергает ключ при
выключенном shuffle, shuffle без ключей и частично отсутствующий ключ; БД отвергает
`repeat_mode = 'sometimes'`. Downgrade: Off/Off проходит с сохранением очереди
(цепочка v16→v11→v16), shuffle или repeat ≠ off — отказ, очередь и счётчик версий
(16) не меняются. `assert_schema` проверяет новые колонки по версиям.

**Правки существующих тестов из-за новой версии.** Счётчики 15→16; в
`audio_mods.rs` снимок очереди до апгрейда с v14 невозможен (репозиторий читает
колонки v16) — заменён явной проверкой полей после миграции и `down(Some(2))`;
в `playlists.rs` откат `down(Some(6))` → `Some(7)` для той же целевой версии.

**Не проверено / расхождения.** Расхождений с планом нет. Физическое поведение
режимов (сервис, сервер, клиент) вне карточки. Отдельный тест
`repeat_launch`-ограничений не добавлен: колонка не имеет бизнес-CHECK по плану.
