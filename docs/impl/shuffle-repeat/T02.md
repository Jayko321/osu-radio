# T02. Серверные команды режимов, shuffle и запуск при shuffle

Состояние: выполнено, проверено (SQLite и PostgreSQL); пользовательская приёмка не проводилась.
Источники: [спецификация](../../specs/shuffle-repeat.md), R1, R5, R6;
[решение: сервис очереди](../shuffle-repeat.md#сервис-очереди-radio-services).
Зависимости: T01 — `RepeatMode`, поля `QueueState`, `QueueEntry.shuffle_order`
и их сохранение в репозитории.

## Результат

Очередь принимает `SetShuffle`/`SetRepeat`; включение shuffle случайно переставляет
записи после текущей, выключение возвращает исходный порядок, вставки и запуск
плейлиста при shuffle ведут себя по R5; снимок и назначение отдают оба режима;
`Clear`, `Recover` и сверка источников режимы не меняют. Поведение Repeat
(переходы, история, `can_next`) — в T03.

## Границы и контекст

- Владение: `crates/radio-services` ([queue.rs](../../../crates/radio-services/src/queue.rs),
  [playlist.rs](../../../crates/radio-services/src/playlist.rs), `Cargo.toml`, тесты
  `src/tests/`). Прямая зависимость `fastrand` (версия из `Cargo.lock`, 2.5.0)
  согласована спецификацией. HTTP и клиент не менять.
- `PlaybackCommand::SetShuffle { enabled }` и `SetRepeat(RepeatMode)` идут через
  `change()` → `apply()` под writer lock; повтор того же значения — no-op без
  новой revision. Режимы не трогают current, token, `launch_source` и историю.
- Включение: всем записям ключ = текущая позиция; записи `next_index()..`
  перемешиваются Fisher–Yates, `reindex()`. Выключение: `next_index()..`
  стабильно сортируются по ключу, ключи очищаются; `Move` ключ не меняет.
- Вставки при shuffle: «Играть следующим» и Play из библиотеки (ветка
  `Change::Command(Play { Some(id) })`) — ключи меньше минимального; «Добавить
  в конец» и `append_playlist_in` — больше максимального; пачка сохраняет внутренний
  порядок; арифметику ключей делать checked. Без shuffle ключи не назначаются.
- `replace_in` получает признак явного старта (вызывает `PlaylistService::play`).
  При shuffle: ключи новых записей в порядке плейлиста; явный старт играет первым,
  все остальные пункты (в том числе стоявшие до него) перемешиваются после него,
  выключение даёт `[C] → A → B → D`; без явного старта перемешивается весь
  плейлист и запускается первая доступная запись нового порядка. Прошлые записи
  сохраняют согласованные ключи. Без shuffle поведение прежнее.
- `QueueSnapshot` и `PlaybackAssignment` получают `shuffle` и `repeat`; опубликовать
  в отчёте имена и типы для T03/T04.

## Проверка и приёмка

Сервисные тесты ([tests/queue*.rs](../../../crates/radio-services/src/tests/)),
SQLite и PostgreSQL. Перестановку проверять по множеству и границам, не по
конкретному порядку:

- `A → [B] → C → D`: после включения те же записи, `A`, `B`, current, token,
  `launch_source` и история прежние; выключение — `C → D`, в том числе после
  `Move` во время shuffle и после `Remove`;
- вставки next/end и Play из библиотеки при shuffle: после выключения —
  сразу после текущей / в конце, прочий порядок исходный;
- плейлист `[A,B,C,D]` с явным стартом `C`: `C` первый, остальные — ровно `A,B,D`
  в любом порядке, выключение даёт `C → A → B → D`; без старта — запускается
  первая доступная запись нового порядка; shuffle off — прежний результат;
- повторная установка режима: revision не растёт; `Clear` и `Recover` сохраняют
  режимы; режимы переживают повторное чтение;
- граница: shuffle при пустой очереди, при 0–1 записях после текущей и при
  остановленной очереди; shuffle не переставляет недоступные записи за текущую.

`cargo test -p radio-db -p radio-services --locked`, PostgreSQL по матрице,
Clippy из матрицы. Существующие queue-тесты проходят без правок поведения.

## Отчёт о выполнении

**Изменённые файлы.** `crates/radio-services/src/queue.rs` (команды, shuffle,
ключи, запуск плейлиста, поля снимка), `playlist.rs` (передаёт признак явного
старта), `lib.rs` (реэкспорт `RepeatMode`), `Cargo.toml` и `Cargo.lock`
(`fastrand = "2.5.0"`, версия уже была в lock-файле; изменилась одна строка
зависимости `radio-services`). Тесты: новый `src/tests/queue_modes.rs`
(подключён из `tests.rs` и `tests/queue.rs`), в `tests/queue_t03.rs` вызов
`replace_in` получил новый аргумент.

**Имена для T03/T04** (`radio_services`):

- `PlaybackCommand::SetShuffle { enabled: bool }`, `PlaybackCommand::SetRepeat(RepeatMode)`
  (`PlaybackCommand` остаётся `Copy`); `RepeatMode` реэкспортирован из `radio_db::model`.
- `QueueSnapshot.shuffle: bool`, `QueueSnapshot.repeat: RepeatMode`;
  `PlaybackAssignment.shuffle: bool`, `PlaybackAssignment.repeat: RepeatMode`
  (у `PlaybackAssignment` добавлен `allow(clippy::struct_excessive_bools)`).
- `QueueService::replace_in(transaction, items, start, explicit_start: bool)` —
  `pub(crate)`; `PlaylistService::play` передаёт `start_item_id.is_some()`.
- Вне `apply()` сервис не тронут: `QueueState.repeat_launch` пока не пишется и не
  читается (это T03). `SetRepeat` только меняет `repeat`.

**Реализация.** `set_shuffle`: включение ставит всем ключ = позиция и
перемешивает `next_index()..` через `fastrand::shuffle`; выключение стабильно
сортирует `next_index()..` по ключу и очищает ключи; повтор того же значения —
no-op без revision (через общее `state != original`). `assign_keys` даёт вставкам
ключи меньше минимума («Играть следующим», Play из библиотеки) или больше максимума
(«Добавить в конец», `append_playlist_in`), арифметика checked, пачка сохраняет
порядок. `replace_in` при shuffle: явный старт ротируется в начало и запускается,
остальное перемешивается; без явного старта перемешивается весь плейлист и
запускается первая доступная запись нового порядка; без shuffle — прежний путь.
`Clear`, `Recover`, `reconcile_sources_in` режимов не касаются.

- `cargo test -p radio-services --locked` — 18 passed, 2 ignored (SQLite).
- PostgreSQL, одноразовый кластер, свежие базы `radio_db_test_services` и
  `radio_db_test_repositories`: `cargo test -p radio-services --no-default-features
  --features postgres --locked -- --include-ignored --skip synthetic_search_timings`
  — 2 passed (`postgres_service_contracts` включает `queue_modes`);
  `radio-db` с `postgres` — 6 passed. Последняя правка тестов после PostgreSQL-прогона
  (замена `assert_eq!(…, true)` на `assert!` и `allow` на длину функции) поведение
  не менялась; на PostgreSQL заново не запускалась.
- `cargo test -p radio-db -p osu-radio-server --locked` — `radio-db` 10 passed,
  `osu-radio-server` 77 passed, 2 ignored.
- Clippy `-D warnings` (`radio-db`, `radio-services`, `osu-radio-cli`,
  `osu-radio-server`) для SQLite и для `--no-default-features --features postgres`,
  плюс `osu-radio-server --features postgres,docs` — чисто.
  `cargo check --workspace --tests` проходит.
- Проверка чувствительности: временная замена ключей «Играть следующим» на «в конец»
  роняет `queue_modes` на сравнении порядка после выключения; код восстановлен.

**Что покрыто (`tests/queue_modes.rs`).** `A → [B] → C → D…`: после включения
те же записи, current, token, `launch_source`, история, режим, Checking-флаг
прежние, `A`/`B` на месте, хвост — то же множество, ключи у всех; после `Move`
и `Remove` во время shuffle выключение даёт исходный порядок без удалённой
записи; повторная установка не растёт revision. 20 циклов on/off на 8 записях —
порядок хотя бы раз менялся и всегда восстанавливался. Границы: пустая очередь
(shuffle включается, добавленная запись получает ключ), остановленная очередь,
0 и 1 запись после текущей, недоступная запись хвоста (перемешивается вместе
с остальными и никогда не становится current). Вставки: next/end-пачки при shuffle
видны сразу и после выключения стоят сразу после текущей / в конце; Play из
библиотеки. Плейлист `[A,B,C,D]`: без shuffle прежний результат; явный старт `C` →
`C` первым, остальные ровно `A,B,D`, выключение даёт `C → A → B → D`; без старта —
все четыре, запущена первая запись нового порядка; запуск поверх истории не
трогает прошлые записи; `append_to_queue` при shuffle сохраняет порядок плейлиста
в конце. Режимы: revision/token, no-op, `playback()`, `snapshot()`, чтение другой
сессией, `recover()` и `clear()` их сохраняют.

**Расхождения и допущения.**

- Пункт приёмки «shuffle не переставляет недоступные записи за текущую»
  двусмыслен. План перемешивает весь `next_index()..` без учёта доступности,
  поэтому недоступные записи перемешиваются как остальные; тест проверяет, что
  они не мешают прошлым/текущей и не запускаются. Если требовалось оставлять
  недоступные на местах — нужно решение пользователя.
- `repeat_launch` и поведение Repeat (переходы, история, `can_next`) — T03;
  в этой карточке `SetRepeat` только сохраняет значение.
- Тест плейлиста создаёт собственную инсталляцию с уникальными хэшами: у общих
  фикстур `snapshot()` хэши битмапов совпадают, и элементы плейлиста схлопываются.

**Не проверено.** Ручной запуск сервера и поведение в клиенте/Qt — вне карточки.
