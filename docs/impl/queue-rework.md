# План реализации переработки очереди

Статус: T01–T09 реализованы; результаты и границы проверок приведены в карточках.
Дата согласования: 2026-10-16. Реализация T01–T09 выполнена; автоматические результаты и границы указаны в карточках. Сквозная приёмка T10 ещё не выполнена.

## 1. Источник и цель

Источник требований — [спецификация очереди](../specs/queue-rework.md), R1–R11.
Цель — единый сохранённый список прошлых, текущей и следующих записей с переходами,
независимыми повторами, добавлением, перестановкой, удалением и двумя очистками.

План содержит согласованные уточнения R3, R7, R10 и R11. При декомпозиции они
синхронизированы с исходной спецификацией, которая остаётся по прежнему пути.

## 3. Техническое решение

### 3.1. Согласованные решения и причины

| Решение | Причина и следствие | Статус |
| --- | --- | --- |
| Отдельная таблица записей очереди | Пользователь выбрал строки вместо JSON всей очереди. Каждая позиция имеет собственную идентичность, порядок и доступность. | Согласовано пользователем. |
| Фиксированный лимит 5000 прошлых записей | Значение выбрано пользователем. Удаляется начало истории по порядку списка; текущая и следующие не ограничиваются. Новая настройка и динамический лимит не добавляются. | Согласовано пользователем. |
| Совместное обновление клиента и сервера | Новый контракт внедряется одновременно; слой совместимости со старыми версиями не нужен. Существующая БД переносится без сброса. | Согласовано пользователем. |
| Отдельные REST-операции | Пользователь выбрал раздельные маршруты вместо общего endpoint команд очереди. | Согласовано пользователем. |
| Асинхронная проверка при добавлении, общий обработчик сервера | Добавление не ждёт файлового ввода-вывода; один управляемый обработчик ограничивает параллелизм и подхватывает незавершённые проверки после перезапуска. | Согласовано пользователем. |
| Play ожидает незавершённую проверку | Запись не пропускается из-за гонки проверки и перехода. Сохраняется намерение играть или оставаться на паузе. | Согласовано пользователем. |
| Проверенные записи не перепроверяются при старте и открытии панели | Дальнейшая недоступность обнаруживается при ошибке воспроизведения или известном изменении библиотеки. | Согласовано пользователем. |
| Плейлист переносится целиком, включая недоступные пункты | Видимый список не теряет такие записи. Play полностью недоступного плейлиста сохраняет новый список и останавливается. | Согласовано пользователем. |
| Возврат источника при повторном импорте восстанавливает доступность | Запись хранит собственный ключ источника; восстановление не зависит от существования плейлиста и не меняет ID, порядок или сохранённую подпись. | Согласовано пользователем. |

Конкретные поля, маршруты и параметры исполнения ниже — техническая детализация
выбранного подхода. Они не вводят новых владельцев состояния или зависимостей.

### 3.2. Данные и миграция

Добавить таблицу записей и новую версионную миграцию. Запись хранит:

- постоянный ID, не используемый повторно после удаления, и позицию в списке;
- ключ источника, nullable-разрешённый audio_source_id и исходный playlist_item_id;
- снимок обычных и Unicode-названий, исполнителя и сведений о сложности;
- состояние доступности и поколение проверки для отбрасывания устаревших результатов.

Singleton-состояние хранит ID текущей записи, границу прошлого/будущего, режим,
revision, playback_token, явный `waiting_for_check` и счётчик выдачи ID.
Уточнение T02: ожидание хранится миграцией 13 отдельно от availability;
активная текущая `checking` при переносе получает ожидание. Ожидание требует
текущую `checking` и Playing/Paused; downgrade отклоняет неоднозначное восстановление.
При наличии текущей записи граница
следует за её позицией. Без текущей записи граница различает прошлое и ещё не
запущенные добавления: после завершения A → B добавленные C → D остаются следующими,
а Play запускает C. ID проходит через Qt/QML без преобразования в неточное число.

Для библиотечного аудио использовать существующую идентичность `(kind, location)`
с сохранением принятого кодирования пути. Для пункта плейлиста сохранять ключ
`(installation kind, hash kind, beatmap hash)` в самой записи очереди. Ссылки на
библиотеку и плейлист не должны каскадно удалять запись очереди. Снимок не хранит
аудиобайты или изображения; даты прослушивания и громкость разрешаются существующими
сервисами отдельно от неизменной подписи.

Миграция переносит каждую старую позицию отдельно, сохраняет порядок, повторы,
положение текущей записи, режим и счётчики. Метаданные восстанавливаются из
существующих пунктов плейлиста/библиотеки там, где доступны; уже утраченные подписи
заменяются явной заглушкой недоступного трека. Разрешённые старые источники без
результата файловой проверки получают незавершённую начальную проверку.

Не очищать библиотеку, плейлисты, даты прослушивания или исходные файлы. Включить
новую таблицу в явный reset и migration lifecycle contracts. Обратная миграция
должна отклонять состояния, которые старый формат не может сохранить без потерь.
После миграции существующее восстановление сохраняет очередь без автозапуска.

Уточнение T04: singleton хранит `launch_source` — audio-ID, точный `SourceType` и
поколение назначенного запуска, четырьмя nullable-полями без FK в новой миграции 14.
Миграции 1–13 не меняются. Для активного запуска без ожидания v13→v14 заполняет
привязку из полной текущей записи; guarded downgrade отклоняет потерю привязки.
При согласовании библиотеки запись очереди получает актуальные ссылки, а назначенный
запуск сохраняет прежние источник и token. Новый token очищает привязку; проверенное
назначение/успех ожидания фиксируют новую. Recovery назначает по актуальной записи
без автозапуска. Даты/громкость assignment и поздний Started относятся к сохранённому
источнику, даже удалённому. Failed меняет доступность только при совпадении его
привязки и поколения с актуальной записью; прежние правила перехода сохраняются.

### 3.3. Изменения и переходы

Все операции выполняются через QueueService под существующей общей блокировкой,
с одним внешним commit. Чтение полной очереди использует согласованный read snapshot;
оно не изменяет состояние и не запускает проверки уже проверенных записей.

- Добавление в конец и следующим сохраняет порядок входного набора и повторы,
  не меняет текущую музыку и паузу. «Следующим» означает непосредственно после
  текущей записи либо на границе будущей части, если текущей записи нет.
- Play записи очереди использует её ID и не добавляет копию. Другая запись получает
  новый токен даже при том же аудиофайле; возобновление текущей после паузы сохраняет
  токен. Play из библиотеки/поиска остаётся отдельной вставкой и запуском по R9.
- Перестановка меняет порядок, но сохраняет текущий ID, токен и локальную позицию
  аудио. Граница прошлого следует за текущей записью.
- Удаление текущей при игре/паузе выбирает следующую доступную либо ожидающую
  проверки запись с сохранением намерения играть/паузы. При отсутствии следующей
  воспроизведение останавливается. Удаление другой записи не перезапускает аудио.
- Очистка следующих сохраняет прошлое, текущую и режим; очистка всего останавливает
  проигрыватель и инвалидирует прежний запуск.
- Запуск плейлиста сохраняет старую часть до текущей включительно и заменяет
  будущую всем плейлистом. Сохраняется выбор стартового пункта. Полностью недоступный
  плейлист сохраняется следующей частью без текущего запуска; музыка останавливается.
  После восстановления источников для запуска нужен явный Play.
- `PlaylistService::append_to_queue(id)` добавляет все пункты в конец без запуска.
  Согласованное уточнение T03: пустой append возвращает прежний assignment без
  изменения revision/token и без обрезки истории; неизвестный плейлист — `NotFound`.
- Пустой Play и неверный явно указанный стартовый пункт сохраняют действующую
  проверку входных данных и не изменяют прежнюю очередь.
- Лимит применяется после изменений порядка/позиции и восстановления состояния:
  остаётся не более 5000 записей до текущей/границы. В конце очереди все пройденные
  записи считаются прошлыми. Недоступные прошлые записи учитываются наравне с другими.
  Само чтение ничего не обрезает.

Revision увеличивается для зафиксированных изменений; no-op и устаревшие события
не создают переходов. Токен меняется при новом запуске или его инвалидации,
а не при обычном редактировании списка или обновлении доступности.

### 3.4. Фоновая проверка доступности

Новые состояния: `checking`, `available`, `unavailable`. Пункт без разрешённого
источника сразу недоступен. Для разрешённого источника добавление фиксирует
незавершённую проверку и будит общий обработчик после commit.

- Обработчик принадлежит жизненному циклу сервера. Рабочий параметр плана —
  не более четырёх одновременных проверок; текущая ожидающая запись приоритетна.
- Проверять обычный файл и возможность открыть его для чтения, без декодирования.
  Переиспользовать правила серверной выдачи аудио, включая защиту от открытия FIFO.
  Файловый ввод-вывод выполняется вне транзакции записи.
- Незавершённые задания определяются сохранёнными состояниями записей; отдельная
  таблица заданий не нужна. После старта подхватываются незавершённые проверки.
  Предусмотреть повторный подбор таких заданий при потере уведомления после commit.
  Это не перепроверка уже доступных записей.
- Результат применяется в короткой транзакции при совпадении ID, поколения проверки
  и привязки источника. Удалённые записи, заменённые источники и более новые
  результаты не затрагиваются. Ошибки задач не должны навсегда оставлять `checking`.
- Результат публикуется через существующие revision-уведомления и playback stream.
  Если `waiting_for_check` текущего запуска установлен, успех снимает ожидание
  без смены token/режима, недоступность переводит дальше с сохранением намерения играть/паузы. Настоящий `Started` приходит от
  аудиодвижка после запуска, а не от проверки файла.
- Изменение доступности само по себе не прерывает уже звучащее локальное аудио.
  Завершение проверки не запускает музыку, добавленную без Play.
- Ошибка воспроизведения помечает соответствующую запись недоступной при совпадении
  привязки/поколения назначенного запуска и обрабатывается с прежней защитой по токену. Удаление источника из библиотеки обновляет связанные
  записи атомарно с изменением библиотеки. Повторный импорт разрешает сохранённые
  ключи заново и передаёт восстановленные источники на фоновую проверку.

Выбранное ограничение: файл, исчезнувший после успешной проверки, может оставаться
отмеченным доступным до ошибки воспроизведения. Перепроверки при открытии панели
или при старте сервера для уже проверенных записей не добавляются.

### 3.5. HTTP-контракты

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/queue` | Полный список записей с собственными ID, снимками, nullable-ссылками и доступностью; текущий ID, граница истории, режим и счётчики из одного read snapshot. |
| `POST /api/queue/items` | `items` и `placement: end \| next`; элемент — типизированная ссылка на audio_source_id либо на конкретный пункт плейлиста. Повторы сохраняются. |
| `POST /api/playlists/{id}/queue` | Добавить весь плейлист в конец, включая недоступные пункты. Разрешение источников и сохранение снимков выполняются сервером в одной операции. |
| `POST /api/queue/items/{entry_id}/play` | Запустить существующую запись без копии; для `checking` сохранить намерение и ждать проверки. |
| `PATCH /api/queue/items/{entry_id}` | Переместить перед `before_entry_id`; null означает конец. Передавать ID опорной записи вместо устаревающего индекса. |
| `DELETE /api/queue/items/{entry_id}` | Удалить конкретную запись с переходом по R5. |
| `DELETE /api/queue/upcoming` | Очистить следующие. |
| `DELETE /api/queue` | Очистить весь список и остановиться. |

Сохранить существующие playback-команды и NDJSON stream. PlaybackAssignment/
PlaybackResponse дополняются текущим ID записи и доступностью. Существующий
`POST /api/playlists/{id}/play` получает семантику R7 с сохранением истории.

Изменения возвращают assignment после commit, затем открытая панель обновляет
полный список. Некорректный ввод отклоняется атомарно, неизвестные ID возвращают
404. Все DTO, проверки полей, безопасные ошибки, оба варианта роутера и OpenAPI
изменяются вместе. Отдельный слой поддержки старых версий не добавляется.

### 3.6. Общий клиент, Qt и моки

QueueViewModel владеет полной проекцией списка, ID записей, статусами и ошибками
операций. Изменения проходят через существующую последовательную полосу команд;
новые параллельные полосы и владельцы состояния не создаются. PlayerViewModel
различает записи по ID и токену, сохраняет выбор при первом восстановленном Paused assignment, ожидает проверки и сохраняет защиту от устаревших
assignment, загрузок, seek и событий аудиодвижка. Ошибка изменения очереди не
перезапускает текущий трек и не заменяет подтверждённый список предположением.

Для Qt использовать отдельный экземпляр существующего TrackListModel с ролями
ID записи, текущей/прошлой позиции и доступности. Ключ строки очереди — ID записи;
audio-ID и playlist-item-ID не уникальны внутри очереди.

Сохранить стиль карточек в существующей панели, заменить Repeater на ListView.
Добавить Play, удаление, перетаскивание и две очистки. При открытии прокручивать
к текущей записи, не меняя выбор и воспроизведение; сохранять клавиатурное
управление, доступные имена, закрытие и восстановление фокуса. Обновления
доступности и медиа не должны сбрасывать прокрутку или обложки видимых строк.

Добавить действия «Добавить в конец» и «Играть следующим» в библиотеку, поиск и
строки плейлиста. Существующее добавление целого плейлиста в конец перевести
на серверную операцию, сохраняющую все пункты и их идентичность.
Обложки и длительности запрашивать для видимых строк существующим ограниченным
планировщиком, сохранив общий кэш и повторное использование медиа одинакового аудио.

Обновить opt-in mock, галерею, HTTP-фикстуры и пробы новых состояний и операций.
Галерея остаётся офлайн, без сессии, файловых проверок, БД и аудиоустройства.
Официальная опора для ListView и drag-and-drop: [ListView](https://doc.qt.io/qt-6/qml-qtquick-listview.html)
и [Qt Dynamic View Ordering](https://doc.qt.io/qt-6/qtquick-tutorials-dynamicview-dynamicview3-example.html).

## 4. Крупные этапы и зависимости

1. **Хранение:** таблица, модели, ключи и снимки, миграция старой очереди, reset
   и repository-контракты. Основа для всех последующих этапов.
2. **Сервисы:** полная проекция, операции, переходы, лимит истории и разрешение
   источников при удалении/импорте. Зависит от этапа 1; проверить атомарность и токены.
3. **Сервер и контракт клиента:** REST-маршруты, общий обработчик проверок,
   уведомления, DTO, ApiClient и фикстуры протокола. Зависит от этапов 1–2.
4. **Клиент и Qt:** обработка действий в существующих VM/координаторе, ожидание
   проверки, панель и меню списков, моки и общая приёмка. Зависит от этапа 3.

На соответствующих этапах обновлять [database](../agent/database.md),
[backend](../agent/backend.md), [frontend](../agent/frontend.md) и необходимые
факты [architecture](../agent/architecture.md). Спецификацию синхронизировать
с согласованными уточнениями и при реализации фиксировать фактический результат
R1–R11 отдельно от запланированной приёмки. Исходный этап `$impl-plan` не включал
создание карточек или изменение продукта; карточки добавлены отдельным этапом ниже.

## 5. Проверка результата

| Требования | Проверки и ожидаемый результат |
| --- | --- |
| R1, R2 | Панель показывает прошлое, текущую и будущее; открытие ничего не запускает. Из A → B → [C] → D → E запустить A: состав и длина сохраняются, далее B и C. Проверить переход в будущее и Previous/Next. |
| R3 | Добавление из библиотеки, поиска и пункта плейлиста в оба положения; пустая, завершённая, играющая и приостановленная очередь. Добавление целого плейлиста включает недоступные пункты и не запускает музыку. После конца A → B добавить C → D, Play запускает C. |
| R4 | Переместить прошлую, текущую и будущую запись, включая повторы одного аудио. Текущий ID и токен сохранены; тестовый движок не открывает файл заново и не сбрасывает позицию. Следующий определяется новым порядком. |
| R5, R6 | Удаление другой записи сохраняет звук. Удаление текущей при игре/паузе с доступным, ожидающим проверки и отсутствующим следующим соблюдает R5. Очистка следующих сохраняет прошлое и текущую; полная очистка останавливает. Библиотека, плейлисты и даты не меняются. |
| R7, R9 | A → [B] → C → D с запуском X → Y даёт A → B → [X] → Y. Проверить запуск после конца и возврата назад, стартовый пункт, частично и полностью недоступные плейлисты. Play B из поиска в [A] → C даёт A → [B] → C; выбор строки без Play ничего не запускает. |
| R8 | Повторы с одинаковыми audio-ID/playlist-item-ID имеют разные ID очереди. Запуск, удаление и перемещение независимы. Перезапуск сохраняет состав, порядок и текущую без автозапуска. Изменение/удаление исходного плейлиста не меняет снимок очереди. |
| R10 | checking блокирует запуск до результата, не нарушая порядок. Проверить файл, отсутствие файла, удаление источника, возврат при импорте, подпись без исходного плейлиста, запоздавший результат после удаления/очистки и смены поколения, ограниченный параллелизм и восстановление незавершённых проверок. |
| R11 | Границы 4999/5000/5001 после переходов, перестановки и восстановления. Текущая и следующие не обрезаются; самые ранние прошлые удаляются. Панель с 5000 прошлыми записями создаёт ограниченное число делегатов и медиазапросов. |

Общий сценарий: запустить плейлист, открыть очередь, вернуться к прошлой записи,
добавить найденный трек следующим, переставить текущую, удалить её на паузе,
запустить другой плейлист, сделать источник недоступным и вернуть импортом,
перезапустить приложение и возобновить вручную. Проверить обе очистки и сохранность
библиотеки, исходных плейлистов и дат прослушивания.

Отдельно проверить миграцию populated versioned-БД без reset, rollback, независимые
подключения, конкурентные изменения, переполнение счётчиков, stale callbacks,
события после остановки обработчика и отсутствие ложных Started при проверках.
Обновить тесты истории прослушиваний, громкости и плейлистов, которые сейчас
рассчитывают на автозапуск при первом append, а также Qt HTTP-фикстуры.

Использовать [матрицу проверки](../agent/development.md#verification-matrix):
SQLite и отдельные временные PostgreSQL-БД `radio_db_test_*`; сервер с docs и без;
клиент с mock и без; последовательные Qt-пробы, QML lint, scoped Clippy,
форматирование и проверку ссылок. Не применять `--all-features`, не использовать
настроенную пользовательскую БД, не запускать неограниченное обнаружение установок.

Для данных нужны временные файлы, разные треки, дубликаты, разные сложности
одного аудио, недоступный пункт плейлиста и управляемая проверка доступности.
Клиентские переходы и отсутствие перезапуска проверять с тестовым аудиодвижком;
работу серверного обработчика — с временными файлами и детерминированными гонками.

При подготовке подтверждены исходники, пути вызовов и состояние рабочей копии;
найдены Rust 1.98.0, Qt 6.12.0 и утилиты PostgreSQL 18.6. Документация Qt получена
через Context7. Сборки, тесты новой очереди, PostgreSQL-кластер и физический
аудиовыход не запускались. Автоматические проверки не заменяют реальный звук
и нативные взаимодействия Linux/Windows; результаты при реализации записывать
отдельно от этой программы проверки.

## 6. Готовность к декомпозиции

Существенные решения согласованы, открытых вопросов, препятствующих декомпозиции,
нет. Рутинные детали SQL, сериализации и локальной реализации остаются исполнителю
в пределах описанных контрактов и существующих границ.

В задачу не входят shuffle, repeat, позиция в секундах между перезапусками,
периодическая перепроверка всех файлов, настройки лимита, копирование аудио,
новые зависимости и общий рефакторинг архитектуры.
