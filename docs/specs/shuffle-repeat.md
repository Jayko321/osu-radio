# Shuffle, repeat и переработка Previous

Статус: поведение согласовано; реализация не начата.
Основание: обсуждение с пользователем в чате 2026-10-24. Ориентиры — Spotify
и YouTube Music; это образец удобства, а не требование воспроизвести их целиком.
Продолжает [переработку очереди](queue-rework.md), где shuffle и repeat были
исключены из объёма.

## Сценарий и результат

Пользователь слушает очередь и хочет перемешать оставшиеся треки, вернуть
исходный порядок, повторять весь список или один трек. Кнопка «Предыдущий»
ведёт себя как в распространённых плеерах: сначала к началу трека, затем
к предыдущей записи. Режимы сохраняются между запусками и доступны из системных
медиаконтролов.

В примерах квадратные скобки обозначают текущую запись: `A → [B] → C`.

## Согласованные требования

### R1. Shuffle

Включение случайно переставляет записи после текущей прямо в списке очереди.
Текущая музыка не прерывается, прошлые записи не меняются, панель показывает
новый порядок. Next/Previous и перетаскивание работают по видимому порядку.

Выключение возвращает все следующие записи в исходный порядок, в том числе
перетащенные во время shuffle. Записи, добавленные во время shuffle через
«Играть следующим», остаются сразу после текущей; через «Добавить в конец» —
в конце. Прошлые записи и текущая при выключении не перемещаются.

Пример: `[A] → B → C → D`; включение даёт, например, `[A] → D → B → C`;
выключение — снова `[A] → B → C → D`.

### R2. Режимы повтора

Кнопка циклически переключает Off → All → One → Off. Состояние различимо
иконкой и доступным именем.

### R3. Repeat One

Естественное окончание трека запускает ту же запись с начала. Повтор
не считается новым прослушиванием: дата последнего прослушивания не обновляется.
Ручные Next/Previous переходят по списку, Repeat One остаётся включённым.

### R4. Repeat All

После последней доступной записи играет первая доступная запись всего списка,
включая прошлые. Next на последней записи тоже переходит к началу.
Повторного перемешивания при этом нет. Previous на первой записи к последней
не переходит (см. R9).

### R5. Добавление и запуск при включённом shuffle

- «Играть следующим» и Play из библиотеки/поиска вставляют сразу после текущей.
- «Добавить в конец» добавляет в конец без перемешивания.
- Запуск плейлиста перемешивает его будущую часть. Явно выбранный стартовый
  пункт играет первым.

### R6. Сохранение режимов

Shuffle и режим повтора — общие для приложения, не для отдельного плейлиста.
Они хранятся в базе данных сервера вместе с состоянием очереди, переживают
перезапуск и не сбрасываются «Очистить всё». Клиент получает их через API
и поток событий очереди.

### R7. Недоступные записи и ошибки

Недоступные записи пропускаются, как сейчас. Ошибка проигрывания при Repeat One
переводит дальше, а не повторяет ту же запись. Если при Repeat All доступных
записей нет, воспроизведение останавливается, а не зацикливается.

### R8. Офлайн-галерея

Галерея показывает и переключает оба режима через клиентские моки без сервера.

### R9. Previous

- Позиция в треке больше 3 секунд: трек начинается с начала. Пауза
  сохраняется; это не новое прослушивание.
- Позиция 3 секунды или меньше: переход к предыдущей доступной записи.
- На первой записи Previous не переходит к последней даже при Repeat All;
  сохраняется текущее поведение — запуск первой записи с начала.
- Правило едино для кнопки, клавиатуры и системных медиаконтролов.

Пример: `A → [B]`, позиция 0:05 — Previous даёт `[B]` с 0:00; позиция 0:02 —
`[A] → B`.

### R10. Системные медиаконтролы

Shuffle и repeat доступны через MPRIS (Linux) и SMTC (Windows): система видит
состояние и может его переключать. Выполняется отдельной карточкой этой задачи.

## Согласованные архитектурные решения

- Режимы и ключ исходного порядка каждой записи хранятся на сервере в состоянии
  очереди; требуется версионная миграция без сброса базы.
- HTTP API и поток очереди получают поля режимов и команды их изменения.
- Прямая зависимость `fastrand` в `radio-services` для перемешивания
  (уже присутствует в `Cargo.lock` транзитивно).
- Порог Previous проверяет клиент: при позиции больше 3 секунд он перематывает
  локально без серверной команды, иначе отправляет обычный Previous.

Конкретные схема, имена полей и HTTP-методы выбираются в техническом плане.

## Границы

- Затрагиваются: хранение и сервис очереди, сервер, общий клиент, Qt-адаптеры
  и панель плеера, моки галереи, медиаконтролы, агентские руководства.
- Сохраняются требования [переработки очереди](queue-rework.md) R1–R11,
  владельцы состояния из [architecture](../agent/architecture.md), защита
  от устаревших событий и атомарность изменений.
- Не входят: «умный» shuffle и рекомендации, режимы для отдельных плейлистов,
  перемешивание прошлых записей.

## Приёмка

| R | Проверка и ожидаемый результат |
| --- | --- |
| R1 | Сервис: `A → [B] → C → D` — shuffle меняет только `C, D`; current/token/история не меняются; выключение возвращает `C → D`, в том числе после перетаскивания; вставки next/end во время shuffle остаются после текущей/в конце. |
| R2 | Qt: цикл Off → All → One → Off, иконка и доступное имя для каждого состояния. |
| R3 | Сервис/клиент: Finished при Repeat One запускает ту же запись с 0; дата прослушивания не меняется; Next/Previous переходят, режим сохраняется. |
| R4 | Сервис: Finished и Next на последней доступной записи запускают первую доступную; порядок не перемешивается. |
| R5 | Сервис: next/end/Play из библиотеки при shuffle; запуск плейлиста с явным стартом и без него. |
| R6 | Перезапуск сервера и клиента сохраняет режимы; «Очистить всё» их не сбрасывает. |
| R7 | Сервис: Failed при Repeat One идёт дальше; Repeat All без доступных записей останавливается. |
| R8 | Галерея: переключение режимов офлайн. |
| R9 | Клиент с подменённым движком: на 5 с Previous перематывает в 0 без серверной команды и без `Started`, на паузе пауза сохраняется; на 2 с отправляет Previous; первая запись не переходит к последней. |
| R10 | Тесты адаптеров MPRIS/SMTC; ручная проверка на Linux и Windows. |

Физический звук и нативное поведение медиаконтролов проверяются вручную.
