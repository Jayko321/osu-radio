# Системное управление воспроизведением: Linux и Windows

Статус: R1–R9 реализованы; Windows automated/native lifecycle проверки выполнены.
Полная нативная и пользовательская приёмка не завершена: Linux runtime и hardware
сценарий обеих ОС не проверены; Qt suite имеет два прежних gallery crash.

## Сценарий и результат

Пользователь запускает osu! radio и управляет воспроизведением через системную
панель плееров и медиаклавиши, в том числе когда окно приложения не в фокусе.
Система показывает текущий трек, его обложку, позицию и состояние воспроизведения.
Управление из приложения и из системного интерфейса согласовано.

Источник требований — обсуждение с пользователем: исходный запрос MPRIS,
уточнение «windows тоже тут делаем сразу» и требование «обьеденить в одну систему
с backend который зависит от платформы». Раздельное управление громкостью в
Windows согласовано отдельно.

Здесь платформенный backend — локальный адаптер системного API на машине клиента.
Это отдельное понятие от HTTP-сервера osu-radio-server.

## Требования

- **R1. Платформы и включение.** Linux и Windows входят в одну задачу.
  Интеграция включается автоматически при запуске приложения: MPRIS на Linux,
  System Media Transport Controls (SMTC) на Windows. Ручной выбор backend и новая
  настройка включения не требуются.
- **R2. Команды.** Поддерживаются Play, Pause, PlayPause, Stop, Next и Previous
  через соответствующие возможности системного API. Доступность действий
  соответствует состоянию плеера и очереди. Обработка команд использует общие
  правила воспроизведения приложения.
- **R3. Данные и синхронизация.** Системе передаются название, исполнитель,
  доступная обложка, известная длительность, позиция и фактический статус
  воспроизведения. Смена трека, пауза, возобновление и остановка отражаются в
  системном интерфейсе. Отсутствующие данные не подменяются вымышленными.
- **R4. Перемотка и громкость.** Перемотка относится к текущему треку; успешное
  изменение позиции из системного интерфейса видно в приложении и наоборот.
  На Windows защита от смены трека начинается при получении callback SMTC:
  событие не содержит идентификатора трека, поэтому действие, доставленное
  самой ОС уже после смены трека, невозможно распознать как старое.
  На Linux MPRIS управляет внутренней громкостью по существующим правилам
  общего и индивидуального уровня. На Windows системный микшер регулирует
  громкость приложения независимо от внутреннего ползунка osu! radio;
  синхронизация этих двух уровней не входит в задачу.
- **R5. Текущий трек и выделение.** Системные команды, метаданные и позиция
  относятся к текущему воспроизведению независимо от выделенного элемента
  библиотеки или плейлиста. Изменение выделения само по себе не меняет системные
  метаданные и не переключает воспроизведение.
- **R6. Режим подключения.** Интеграция работает с локальным и удалённым
  сервером, отражая воспроизведение на машине клиента. Удалённый режим сохраняет
  существующие правила: клиент не запускает и не останавливает удалённый сервер.
- **R7. Единая система.** Общая часть определяет команды, метаданные, состояние
  и доступность действий. Платформенный backend выбирается по ОС и переводит
  данные и события между общим контрактом и системным API. Правила
  воспроизведения не дублируются в Linux- и Windows-адаптерах.
- **R8. Существующие владельцы состояния.** Интеграция использует AppController,
  существующую очередь и состояние текущего воспроизведения. Отдельная очередь
  или независимый владелец состояния плеера не создаются. Сохраняются границы
  между сервером, клиентом, аудиодвижком и GUI.
- **R9. Ошибки и завершение.** Отсутствие D-Bus или ошибка платформенной
  интеграции не мешают запуску, музыке и интерфейсу. Фатальная ошибка отключает
  только интеграцию до следующего запуска приложения с диагностикой;
  автоматическое повторное подключение не требуется. Ошибка отдельной обложки
  не отключает остальное системное управление. При завершении приложения
  освобождаются системная сессия и обработчики; приложение перестаёт быть
  доступным для системного управления.

## Примеры и граничные случаи

1. Играет A, пользователь выделяет B в библиотеке или плейлисте. Системная
   панель продолжает показывать A; Pause ставит на паузу A, перемотка меняет
   позицию A. B не запускается от изменения выделения.
2. Пользователь ставит текущий трек на паузу медиаклавишей, затем возобновляет
   его из приложения. Системная панель и приложение показывают одно фактическое
   состояние и актуальную позицию.
3. Во время запроса перемотки A сменяется на B. Запоздалый запрос не перематывает
   B по позиции, предназначенной для A. На Windows это гарантируется для смены
   трека после получения callback SMTC, с ограничением API из R4.
4. Очередь пуста либо следующего/предыдущего трека нет. Система отражает
   доступность команд; вызов недоступного действия не ломает плеер.
5. У трека нет обложки или неизвестна длительность. Остальные данные и команды
   продолжают работать; обложка предыдущего трека не выдаётся за текущую.
6. В Windows пользователь меняет громкость приложения в системном микшере.
   Внутренний ползунок osu! radio сохраняет своё значение. На Linux изменение
   громкости через MPRIS отражается во внутренней громкости и наоборот.
7. GUI подключён к серверу на другой машине. Системная панель и медиаклавиши
   управляют клиентом, на котором воспроизводится звук; закрытие GUI освобождает
   интеграцию и не останавливает удалённый сервер.

## Существующие механизмы и границы

- [AppController и AppCommand](../../crates/osu-radio-client/src/controller.rs)
  предоставляют общий цикл событий, команды управления и завершение.
- [PlayerViewModel](../../crates/osu-radio-client/src/view_models/player.rs)
  различает выбранный и текущий трек, обрабатывает назначения и доступность
  управления. Текущий GUI-путь seek_selected зависит от выделения: его нельзя
  без проверки использовать для системной перемотки из R5.
- [Playback и локальный worker](../../crates/osu-radio-client/src/playback.rs)
  содержат фактический снимок аудиодвижка, идентификаторы текущего элемента,
  playback_token и seek_serial. Защита от устаревших команд должна сохраняться.
- [Qt AppBridge](../../apps/osu-radio-qt/src/app_bridge.rs) связывает приложение
  с контроллером. GUI владеет нативным окном и представлением изображений;
  Qt-типы и UI-ресурсы не переносятся в общие VM.
- [Архитектура](../agent/architecture.md) и
  [frontend guide](../agent/frontend.md) определяют существующих владельцев
  очереди, локального аудио, медиаданных и жизненного цикла.
- Существующие проверки находятся в
  [controller tests](../../crates/osu-radio-client/src/controller/view_model_tests.rs)
  и [playback tests](../../crates/osu-radio-client/src/playback.rs).
  Они не доказывают подключение к MPRIS или SMTC.

Общая координация остаётся в toolkit-free клиенте. Платформенные адаптеры
используют существующие команды и состояние, сохраняя текущий аудиодвижок.
Согласованные зависимости, границы нового crate и способ подключения нативного
окна зафиксированы в [техническом плане](../impl/system-media-controls.md);
эта спецификация не дублирует детали реализации.

В объём не входят экспорт всей очереди и плейлистов через системные интерфейсы,
новые shuffle/repeat, открытие произвольных URI и синхронизация системного микшера
Windows с внутренней громкостью. Офлайн-галерея сохраняет существующую изоляцию
от live-сессии. Изменения HTTP-контрактов, схемы хранения и серверной очереди
данной спецификацией не предусматриваются.

## Приёмка

Окружение: Linux с пользовательской D-Bus-сессией, системным MPRIS-клиентом и
панелью плееров; Windows с SMTC и системным микшером; медиаклавиши; треки с разными
метаданными и доступной обложкой, а также без обложки/известной длительности.
Проверяются локальный и удалённый режимы подключения с явно заданными источниками.

| Требование | Наблюдаемый критерий |
| --- | --- |
| R1 | Приложение автоматически обнаруживается системным интерфейсом на каждой ОС; ручной выбор backend не нужен. |
| R2 | Системные команды и медиаклавиши выполняют ожидаемые действия, включая работу без фокуса окна; доступность соответствует текущей очереди. |
| R3 | Метаданные, обложка, статус и позиция соответствуют текущему воспроизведению и обновляются при изменениях; неполные данные обрабатываются корректно. |
| R4 | Перемотка согласована в обе стороны и не применяется к сменившемуся треку с учётом границы callback SMTC из R4; громкость соответствует отдельным правилам Linux и Windows. |
| R5 | Сценарий «играет A, выбран B» сохраняет метаданные и управление A в библиотеке и плейлисте. |
| R6 | Системное управление работает при обоих режимах подключения; завершение удалённого клиента не останавливает сервер. |
| R7 | Одинаковые события платформенных адаптеров приводят к одинаковым общим действиям; платформенные различия ограничены системным API. |
| R8 | Проверка кода подтверждает существующих владельцев состояния; системные действия проходят через общий контроллер без отдельной очереди или аудиодвижка. |
| R9 | Ошибка подключения системного API не нарушает воспроизведение; выход освобождает обработчики и доступную для управления системную сессию. |

Основные риски: управление выделенным вместо текущего трека, устаревшая
перемотка при смене назначения, расхождение опубликованного и фактического
состояния, оставшиеся обработчики после выхода. Общие правила проверяются
автоматически с переиспользованием существующих тестов; подключение и обмен
платформенных адаптеров требуют отдельных интеграционных проверок. Реальная
системная панель, медиаклавиши и аудиовыход проверяются нативно на обеих ОС.
Сборка и тесты с заменами системного API не заменяют такую приёмку.

## Состояние и свидетельства

- Требования R1–R9 согласованы в чате. R1 расширен с Linux до Linux и Windows;
  R4 уточнён: громкость системного микшера Windows независима от внутренней,
  защита перемотки SMTC начинается при получении callback. Для R9 согласовано
  отключение интеграции до перезапуска без автоматических повторов.
- Общая система с платформенными backend и существенные решения реализации
  согласованы в [техническом плане](../impl/system-media-controls.md).
  Открытых продуктовых вопросов нет.
- Реализация T01–T06 интегрирована: общий контракт и native lifecycle в
  [media-controls](../../crates/osu-radio-media-controls/src/lib.rs), правила в
  [client coordinator](../../crates/osu-radio-client/src/controller/system_media.rs)
  и [Player VM](../../crates/osu-radio-client/src/view_models/player.rs), current
  artwork в [общем медиаконвейере](../../crates/osu-radio-client/src/controller/media.rs),
  автоматическое подключение/отключение в
  [Qt lifecycle](../../apps/osu-radio-qt/src/runtime.h).
- При подготовке сверены
  [MPRIS 2.2](https://specifications.freedesktop.org/mpris/latest/),
  [MPRIS Player](https://specifications.freedesktop.org/mpris/latest/Player_Interface.html),
  [Windows SMTC](https://learn.microsoft.com/en-us/uwp/api/windows.media.systemmediatransportcontrols)
  и [SMTC GetForWindow](https://learn.microsoft.com/en-us/windows/win32/api/systemmediatransportcontrolsinterop/nf-systemmediatransportcontrolsinterop-isystemmediatransportcontrolsinterop-getforwindow).
- Финальные команды/ограничения 2026-10-18 записаны в
  [T07](../impl/system-media-controls/T07.md#отчёт-о-выполнении); команды для
  повторения — в [development guide](../agent/development.md#system-media-controls-verification).
  Выполнены на Windows MSVC Rust 1.98.0, Qt 6.8.3. Linux cross-target check/Clippy
  компилируют all-targets, но не исполняют Linux unit/D-Bus tests.

| Требования | Реализация и автоматические свидетельства | Нативные свидетельства и предел |
| --- | --- | --- |
| R1 | Target dispatch T01, MPRIS T03, SMTC T04, live-only Qt attach T06 | Windows: две реальные HWND-пробы и native Qt smoke прошли. Linux обнаружение через bus/панель не выполнялось. |
| R2 | T02 current transport/capability matrix; T03 protocol harness подготовлен; T04 conversions | Публикация кнопок SMTC прочитана через GetForWindow. Системный ввод без фокуса и физические медиаклавиши не проверены. |
| R3 | T02 assignment/worker metadata/status/position; T05 current encoded cover и stale response tests | Windows HWND harness прочитал native metadata/thumbnail, очистил старые поля. Рендеринг панели, physical playback/timeline readback и Linux protocol execution не проверены. |

Seek из реальной панели, Linux Volume через bus и независимость Windows mixer в пользовательском сценарии не проверены. |
| R5 | T02 A current/B selected в library/playlist; T05 невидимый current cover, отдельный cover GUI-дубликата и generation/token guards | Клиентские fixtures пройдены; полный live desktop A/B-сценарий не выполнен. |

Не проверено физическое remote playback. |

| R8 | Один AppController/event loop и существующие VM/worker/PendingPlayback/media lanes; HTTP/DB контракты не менялись | Проверка исходников и client suites: 159 normal/175 mock passed, по 2 ignored benchmarks. |
| R9 | T01 terminal failure/acknowledged shutdown/artwork cleanup; T02 продолжение работы клиента; T05 нефатальные covers; T06 lifecycle barrier | Windows native Close/quit/failed-launch: detach при живом HWND, Disabled после ack, затем destroy; удалённая fixture сохранилась. Linux fatal/unavailable bus harness подготовлен, не исполнен. |

Строгий integrated Clippy normal и mock+Qt, `cargo fmt --check` и whitespace
прошли. Serial Qt suite: **13 passed, 2 failed, 2 ignored**. Два existing gallery
сценария `controls`/`controls-popups` завершают QML assertions, затем падают
`0xc0000005`; T06 воспроизвёл те же exit codes на release executable до функции.
Suite не зелёный; тесты не ослаблены. Отдельные native Qt и реальный local backend
probes прошли. В Linux CI добавлены scoped tests/Clippy media-controls и явный
изолированный D-Bus запуск; hosted CI здесь не исполнялась.

Открытая приёмка: реальный Linux desktop/session bus/MPRIS, системные панели,
медиаклавиши и физический аудиовыход на обеих ОС, двусторонний seek и правила
громкости в полном live сценарии. Успешная публикация HWND, fake worker и offscreen
не подтверждают эти критерии. **Пользовательское принятие не заявляется.**
